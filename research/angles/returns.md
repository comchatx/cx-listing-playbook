# Returns and after-sale signals

Read 2026-10-14 by the research seat. Tags: [official] Amazon's own page or document; [opinion] a named practitioner; [research] published research; [seat] the seat's own reasoning, never a skill position.

## What this covers

**Stage:** conversion and post-purchase. A return is the buyer's verdict on what the listing promised. Returns do not measure exposure or click-through. They measure whether the conversion stage was earned honestly: what the title, images, bullets, size chart and compatibility statements led the buyer to expect, against what arrived. Amazon also feeds returns back into the conversion stage in two ways. The "frequently returned item" badge shows on the detail page itself, and CX Health and NCX can close an offer (see the rules below).

**Skills it feeds:**
- `listing-review`: returns are trigger family 3 (the product's own signals: "return rate up, negative-review themes concentrated", roadmap §1.1). The skill needs to know which return reasons a listing change can address and which it cannot, which file holds each figure, and that some figures exist only in Seller Central with no API.
- `listing-change-log`: a change made because of returns has to record the reason distribution before the change, the claim the change adds or corrects, and an observation window long enough for returns to arrive.
- `effect-review`: return figures lag more than any other metric on the route, which is up to about 45 days for Amazon's own per-ASIN return rate. They are dated by ship date in one source and by return date in another, and the holiday return window stretches them further. An effect review that reads a recent return rate as an improvement is reading missing data.
- The report script: `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA` and the seller-fulfilled returns reports are create → poll → download reports. Their names, options and waits belong to `door.md`.

**Why a senior operator cares:** return reasons are the cheapest customer research a seller gets. A cluster of "not as described", "not compatible" or "too small" on one ASIN usually means a listing defect, while "defective" and "damaged" usually do not. Returns also cost money twice: the returns processing fee above a category threshold, and the badge on the detail page. In the day-2 run with no method, cx proposed "expectation-management copy" for the store's refund rate and promised a drop to a "category average". It did this without having read a single return reason, and gave no source for the average. Reading the reasons was listed as a later to-do (`20261014-0921-beta-browser-listing-run-day-2.md`, proposal row 10). That is the failure this angle exists to prevent.

## Amazon's own rules and guidance

### Which file holds which return

- **The FBA returns report.** `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA`, "FBA Returns Report": "Contains customer returned items received at an Amazon fulfillment center, including Return Reason and Disposition." "This report can only be requested." Latency: "Content updated daily." Roles listed: Pricing, Amazon Fulfillment. No maximum date range is stated on the page. A return appears only once the unit is *received at a fulfillment center*. A return still in transit is not in it yet, and a refund without a return is never in it. [official] (Fulfillment by Amazon (FBA) Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-fba, read 2026-10-14.) The "received at" consequence is [seat] inference from the description.
- **Related FBA reports.** `GET_FBA_FULFILLMENT_CUSTOMER_SHIPMENT_REPLACEMENT_DATA` ("FBA Replacements Report", "Contains replacements that have been issued to customers for completed orders", "For FBA sellers only", NA and IN stores) and `GET_FBA_REIMBURSEMENTS_DATA` ("itemized details of a seller's inventory reimbursements, including the reason for the reimbursement"). Both are request-only and updated daily. [official] (same page.)
- **The seller-fulfilled returns reports.** Six types on "Returns Reports": `GET_XML_RETURNS_DATA_BY_RETURN_DATE` and `GET_FLAT_FILE_RETURNS_DATA_BY_RETURN_DATE` ("Contains detailed returns information, including return request date, RMA ID, label details, ASIN, and return reason code"), the two Seller Fulfilled Prime variants (`GET_XML_MFN_PRIME_RETURNS_REPORT`, `GET_CSV_MFN_PRIME_RETURNS_REPORT`), and the two return-attribute variants (`GET_XML_MFN_SKU_RETURN_ATTRIBUTES_REPORT`, `GET_FLAT_FILE_MFN_SKU_RETURN_ATTRIBUTES_REPORT`, "prepaid label eligibility and returnless refund eligibility"). All six: "This report can be requested or scheduled." "You can request up to 60 days of data in a single report." Rule of coverage, verbatim: "These reports only cover seller-fulfilled order returns. They do not include:" "FBA returns. Use the FBA Returns Report (`GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA`) instead." and "Returnless refunds". Every type lists "Direct to Consumer Shipping (Restricted)" among its roles, next to "Inventory and Order Tracking", and some add "Pricing". The page does not say whether a restricted role is required or only one of the roles is. [official] (Returns Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-returns, read 2026-10-14.)
- **Amazon's per-ASIN return rate (Data Kiosk).** In the seller analytics dataset `analytics_sellerAnalytics_2025_03_31`, the `returns` group has `returnedUnits`, `totalRefundAmount` and `returnedRate`. The guide says: "Returns are attributed to the day the returned unit was shipped, not the day it was returned." "Return data is computed with a delay of about 45 days", so `returnedUnits` and `totalRefundAmount` "for the most recent ~45 days may be null or incomplete", and "`returnedRate` may appear artificially low for recent dates, because returned units lag while shipped units are current." `returnedRate` is "not supported in `totals`". The same page says "All metrics in the seller analytics dataset are ready after 34 hours", and the 45-day statement overrides that for returns. [official] (Seller Analytics Dataset Use Case Guide, https://developer-docs.amazon/sp-api/docs/seller-analytics-dataset-guide, read 2026-10-14.) The schema adds that `returnedUnits` counts units "returned by customers with a resolution (refund or replacement), including returnless refunds, mapped to the day each unit was shipped", and that `returnedRate` is "returned units / shipped units". Its field descriptions repeat the delay ("Return data is computed with a delay of about 45 days, so the most recent ~45 days may be empty or incomplete"), and the `returns` group carries `@paamRights(require: ["analytics_sales_and_traffic_view_pa"])`. [official] (`schemas/data-kiosk/analytics_sellerAnalytics_2025_03_31.graphql`, github.com/amzn/selling-partner-api-models, main branch, read 2026-10-14, re-read in the reconciliation.) The 45-day figure is for human readers. The guide and the schema state it, and cx reads it from them at run time.
- **Amazon's return-defect topics (Data Kiosk).** The same dataset has a `defects` group: "Return-defect analytics derived from customer returns". `defects.topics` gives per topic a `returnDefectTopic`, a `returnDefectFrequency` (trailing six months), a `returnDefectContribution` (fraction of the product's return defects) and `returnDefectRecommendations` ("Recommended actions to address the return defects associated with this topic"). "The `defects` metrics are snapshots computed over a trailing six-month window, not period sums"; "Each product carries one return-defect topic per snapshot; a topic can change from one snapshot to the next." Sales-and-traffic access covers this group, and the schema marks it `@paamRights(require: ["analytics_sales_and_traffic_view_pa"])`. [official] (Seller Analytics Dataset Use Case Guide; the schema file above.) Under `accountHealth` the schema also carries trailing-120-day regional defect rates, among them `regionInaccurateProductDefectRateT120Days` ("Regional defect rate for products with inaccurate product information over the past 120 days (snapshot data, always returns latest value)"). [official] (schema file.) What feeds "inaccurate product information" is not stated.
- **Refunds in the Sales and Traffic report.** In `GET_SALES_AND_TRAFFIC_REPORT`, `unitsRefunded` and `refundRate` are in `salesByDate` only, which is store-wide by date. `salesByAsin` has no refund field. The report schema describes `refundRate` as "calculated by dividing unitsOrdered by unitsRefunded", which is the division upside down. The Data Kiosk Sales and Traffic dataset (`analytics_salesAndTraffic_2024_04_24`) has `unitsRefunded` and `refundRate` per ASIN as well as per date, and there the description reads "calculated by dividing unitsRefunded by unitsOrdered". [official] (`schemas/reports/sellerSalesAndTrafficReport.json` and `schemas/data-kiosk/analytics_salesAndTraffic_2024_04_24.graphql`, selling-partner-api-models main, read 2026-10-14.) A refund is not a return: a refund can be returnless, and a received return can be unrefunded. [seat]
- **Refunds in Finances.** The Finances v0 model has `RefundEventList` ("A list of refund events") among the financial events. A refund item carries `ItemChargeAdjustmentList` and `ItemFeeAdjustmentList`, "only returned for refunds, guarantee claims, and chargeback events". [official] (`models/finances-api-model/financesV0.json`, read 2026-10-14.)

### Return topics through the API (Customer Feedback API)

- The API page says "Return insights are only available at the browse node level", while review insights are at both ASIN and browse-node level. Operations: `getItemBrowseNode`, `getBrowseNodeReturnTopics`, `getBrowseNodeReturnTrends`, `getItemReviewTopics`, `getItemReviewTrends`, `getBrowseNodeReviewTopics`, `getBrowseNodeReviewTrends`. "The data provided by the Customer Feedback API is refreshed weekly." Stores: US, UK, FR, IT, DE, ES, JP. The API is in English only. Role: Brand Analytics or Selling Partner Insights. [official] (Customer Feedback API, https://developer-docs.amazon/sp-api/docs/customer-feedback-api, read 2026-10-14.)
- The model gives `getBrowseNodeReturnTopics` as "Retrieve the topics that customers mention when they return items in a browse node", with at most 10 topics, each with an `occurrencePercentage` ("The percentage of feedback that mentions the topic") for `allProducts` in the node. `getBrowseNodeReturnTrends` gives monthly points. Review trends cover "the past six months". The sandbox example topics include "Weak fragile", "Assembly/Installation", "Quality-Overall" and "Value for Money". [official] (`models/customer-feedback-api-model/customerFeedback_2024-06-01.json`, read 2026-10-14.) **This contradicts the lead** "Customer Feedback API return topics" if the lead meant per ASIN. The API gives the category's return themes, not the product's own.
- Release note, June 25, 2025: the Customer Feedback API "retrieves insights from customer reviews and returns". Release note, September 30, 2026: the seller analytics dataset gives "sales, traffic, promotions, account health, search, reviews, defects, and returns". [official] (SP-API release notes, https://developer-docs.amazon/sp-api/docs/sp-api-release-notes, read 2026-10-14, first 100,000 characters.)

- **The reason is the buyer's label, not a finding.** "The order return reason you see for refunded orders is as the buyer selected from a standard list of options when initiating their return request. ### The January return wave as a window artefact (gap fill)

The sources disagree on which date a return carries. That is what turns the holiday window into an artefact in a before/after comparison:

- **Dated by return or processing date:** the FBA returns report (`return-date` = "Date returned merchandise was processed at the fulfillment center"; FBA Customer Returns report (overview)) and the seller-fulfilled returns reports "by return date" (Returns Reports, first pass). In these files, units shipped in November and December and returned under the extended window land in January.
- **Dated by ship date:** the Data Kiosk `returns` group ("attributed to the day the returned unit was shipped"; Seller Analytics Dataset Use Case Guide) and Returns and Recovery Insights' return rate ("calculated based on the ship date, with a 45-day delay"). In these, the same returns land back on the November and December ship dates, and they keep arriving there until well after January 31.
- **Dated by ship month plus two calendar months:** the returns processing fee's return rate ("the percentage of the product's shipped units in a given month that are physically returned during that month and the subsequent two calendar months"; 2026 returns processing fee changes). For December shipments, that window runs to the end of February.

Amazon states each of these dating rules. [official] (pages as named.) The consequences below are [seat] inference from them, not an Amazon statement:

- A January return spike in a return-dated file is partly December's sales coming back. It is not evidence that a January listing change raised returns.
- A ship-date return rate for November–December read in January is incomplete twice over: once for the extended window and once for Amazon's stated delay. It will read low, as the dataset guide warns for recent dates generally.

No Amazon page states a January return volume or rate. The figures practitioners give are listed under practitioners and are unsourced.

### The returns processing fee (RULE, enforced as a charge)

- **The lead is contradicted.** The high-return-rate fee is not a 2025 change and it does not target apparel and shoes. Amazon announced on December 5, 2023 that it "will expand the returns processing fee" to high-return products in all categories "excluding apparel and shoes", starting June 1, 2024, for "products that have the highest return rates relative to other products in their category". It also said "Existing returns processing fees for apparel and shoes will remain unchanged on average", and gave the rationale "This fee will address the operational costs of returns and reduce waste." [official] (Amazon Selling Partners, "Update to US referral and Fulfillment by Amazon fees", Dharmesh Mehta, December 5, 2023, https://sellingpartners.aboutamazon.com/Update%20to%20US%20referral%20and%20Fulfillment%20by%20Amazon%20fees, read 2026-10-14.)
- **Mechanics.** The fee applies only above the threshold for the product's fee category, and then to each returned unit above it. Returns are tracked for the month a product shipped plus two calendar months, and the fee is charged after that three-month period. There is no fee in months when a product ships fewer than 25 units. The New Selection program waives the first 20 returned units above the threshold. The "Return Insights dashboard" on the FBA Returns page shows the returned units, return rates and thresholds used. Amazon staff added: "If a return is the result of Amazon's error, it will not be included in the fee calculation." [official] (Seller Forums News, "Updates to the Return Insights dashboard and Returns Processing Fee reminder", News_Amazon, https://sellercentral.amazon.com/seller-forums/discussions/t/4ba71c53-681d-49e8-ab4d-5a533b0072af, read 2026-10-14.)
- **Later years.** The 2025 fee update (November 19, 2024) does not mention returns. ## Published research

- [research] Hao-Fei Cheng, Eyal Krikon, Vanessa Murdock (Amazon), "Why Do Customers Return Products? Using Customer Reviews to Predict Product Return Behaviors", ACM CHIIR 2024, pp. 12–22, doi 10.1145/3627508.3638326. A review-text classifier (fine-tuned BERT) improves return-reason prediction by "more than 20% average precision" over a baseline without review text, and the authors "show that reviews can be used to identify nuanced return reasons beyond what the customer indicated." The authors are Amazon's and the paper is listed on Amazon Science, but neither the abstract nor the Amazon Science page names the data source. **Transfer:** high in kind if the data are Amazon's, which is likely but unconfirmed from what was read. The selected reason code is a coarse label, and reviews hold the detail. The seller cannot run the model, but the Customer Feedback API's review topics and VoC's root causes are Amazon's productized analogue ([seat]).
- [research] Yili Hong, Paul A. Pavlou, "Product Fit Uncertainty in Online Markets: Nature, Effects, and Antecedents", Information Systems Research 25(2):328–344, 2014, doi 10.1287/isre.2014.0520. Relative to product quality uncertainty, product fit uncertainty (whether the product's attributes match the buyer's preference) "has a significantly stronger effect on product returns". In the same study, online product forums moderate the effect of experience goods on *fit* uncertainty, while website media (visualization) "attenuate the effect of experience goods on product *quality* uncertainty" — not fit uncertainty. **Transfer:** moderate. The data come from buy-it-now auctions, not Amazon, but the fit-versus-quality split maps onto the listing-fixable versus product-defect split.
- [research] Nachiketa Sahoo, Chrysanthos Dellarocas, Shuba Srinivasan, "The Impact of Online Product Reviews on Product Returns", Information Systems Research 29(3):723–738, 2018, doi 10.1287/isre.2017.0736. At one multichannel specialty retailer, more helpful reviews were associated with fewer returns, and products shown with ratings above their true level were returned more often. (Abstract read through OpenAlex; the journal page was 403.) **Transfer:** moderate. It is one retailer, but it supports the idea that over-promising raises returns.
- [research] Prabuddha De, Yu Jeffrey Hu, Mohammad Saifur Rahman, "Product-Oriented Web Technologies and Product Returns: An Exploratory Study", Information Systems Research 24(4):998–1010, 2013, doi 10.1287/isre.2013.0487. On one women's-clothing retailer's data, zoom use was associated with fewer returns, alternative photos with more returns and lower net sales, and colour swatches showed no clear effect. **Transfer:** low to moderate. It is one apparel retailer, and it warns that "more images" is not automatically fewer returns.
- [research] Vivek Sembium, Rajeev Rastogi, Atul Saroop (Amazon), Srujana Merugu, "Recommending Product Sizes to Customers", RecSys 2017, pp. 243–250, doi 10.1145/3109859.3109891. On Amazon shoe datasets, a latent-factor model learnt from purchase and return data, leveraging return codes, showed "an improvement of 0.49% in percentage of Fit transactions over control" in an online A/B test (a 17–21% AUC gain offline). **Transfer:** this is Amazon's size recommendation, a lever owned by Amazon, not the seller. It tells the reader that size returns respond to better size information.
- [research] J. Andrew Petersen, V. Kumar, "Are Product Returns a Necessary Evil? Antecedents and Consequences", Journal of Marketing 73(3):35–51, 2009, doi 10.1509/jmkg.73.3.035. The authors "demonstrate that product returns are inevitable but by no means evil", studying the consequences of returns for future customer and firm behaviour. **Transfer:** low (a single non-Amazon retailer; the abstract read does not name the retailer type, so "catalogue retailer" is unverified). It is a caution against treating a return rate of zero as the goal.
- [research] Sergey Turlo, Katharina Kessing, "Getting consumers to learn more about the product – The Effect of informative return labels on information processing and return rates", Proceedings of the European Marketing Academy, 54th (2025), extended abstract 126111. An analytical model plus an experiment find that "frequently returned items" labels change how much effort consumers spend on product information, conditional on their prior belief that the product fits. **Transfer:** directly about the badge's mechanism, but it is an extended abstract with no effect sizes given.
- No peer-reviewed study was found that measures the conversion effect of Amazon's badge itself.
- **Gap fill, the January wave:** no peer-reviewed study was found that measures post-holiday return timing on a marketplace. A web search turned up only consumer surveys reported in the press, which are not cited here. Janakiraman, Syrdal & Freling, "The Effect of Return Policy Leniency on Consumer Purchase and Return Decisions: A Meta-analytic Review", Journal of Retailing 92(2):226–235, 2016, doi 10.1016/j.jretai.2015.11.002, is the obvious candidate on how a longer return window changes returns. Its abstract could not be read (Crossref and Semantic Scholar have no abstract; ScienceDirect returned HTTP 403), so no finding is cited from it.

## Stable enough for a skill

- FBA returns and seller-fulfilled returns live in different reports, and neither contains the other. The seller-fulfilled returns reports exclude returnless refunds. (Returns Reports; Fulfillment by Amazon (FBA) Reports.)
- The FBA returns report lists units received back at a fulfillment center, with a customer-chosen reason, a customer comment where one exists, and a disposition. (Fulfillment by Amazon (FBA) Reports; "View insights on your FBA returns".)
- Amazon's own per-ASIN return rate (Data Kiosk seller analytics) is dated by the day the unit shipped and arrives with a lag Amazon states in the dataset guide and the schema. The most recent weeks are incomplete and read low. (Seller Analytics Dataset Use Case Guide; analytics_sellerAnalytics_2025_03_31 schema.)
- The Customer Feedback API gives return topics for a browse node, never for one ASIN. Review topics exist per ASIN. (Customer Feedback API; customerFeedback_2024-06-01 model.)
- The `GET_SALES_AND_TRAFFIC_REPORT` refund figures are store-wide by date. Per-ASIN refunds come from the Data Kiosk Sales and Traffic dataset. (Report and dataset schemas.)
- VoC (CX Health, NCX return rate, the badge column, at-risk ASINs, suggested return rate) and Fit Insights are Seller Central pages, and no SP-API operation for them was found. (Forum announcements; [seat] for "no operation found".)
- The badge is relative to similar products in the category, and Amazon removes it when the return rate falls back in line. Amazon publishes no threshold. (Seller Forums, "Frequently returned item"; "Track and prevent product return badges".)
- The high-return-rate returns processing fee excludes apparel and shoes, which have their own returns processing fees. Thresholds are per fee category and live on Amazon's fee page. (Update to US referral and Fulfillment by Amazon fees; Return Insights reminder.)
- Return windows run past delivery, and Amazon extends them for holiday purchases. Returns for a period keep arriving long after it ends. (sell.amazon.com returns blog; holiday window announcements.)
- Amazon names inaccurate or incomplete detail pages, sizing and compatibility as causes of returns that the seller can address in the listing. (sell.amazon.com returns blog; VoC 2018 text; Fit Insights.)
- *Gap fill:* The FBA returns report's reason is the one the buyer picked from a standard list. Amazon says it may not reflect what really happened, and decides reimbursement on the unit's graded condition instead. (FBA customer returns policy.)
- *Gap fill:* In some stores, Amazon structures the customer comment as Base Issue | Issue Detail | Product or Listing Insight. The Listing Insight part says whether listing content may have led to a wrong-item, missing-parts, not-as-expected or size/fit return. (FBA Customer Returns report (overview); FBA Returns page.)
- *Gap fill:* Refunds without a return are absent from the FBA returns report but count toward the ASIN's return rate. (FBA Customer Returns report (overview); FBA Returnless Resolutions.)
- *Gap fill:* Amazon keeps at least four different return rates: the overall rate (Returns and Recovery Insights; Data Kiosk), the fee's rate, the badge's rate and the NCX return rate. Each has its own definition, dating and refresh, so a rate is named by its source. (Returns and Recovery Insights; 2026 returns processing fee changes; Frequently returned item badge; Voice of the Customer.)
- *Gap fill:* The badge compares an ASIN with similar ASINs against a suggested return rate that changes over time. Amazon removes the badge automatically, and it may remove it earlier on a consistent downward trend. No fixed threshold or recovery period is published. (Frequently returned item badge.)
- *Gap fill:* The badge's rate counts only returns attributable to the seller and is updated monthly, so it can differ from the overall return rate. (Returns and Recovery Insights.)
- *Gap fill:* Amazon has a low-return counterpart to the badge, which it calls the Frequently Kept badge. (Returns and Recovery Insights.)
- *Gap fill:* Outside apparel and shoes, the returns processing fee is charged only on returned units above a per-category threshold. The return rate it uses counts physical returns over a measurement window that starts in the ship month and runs past it, and the fee is billed after that window closes. Apparel and shoes are charged on every returned unit. The window, the billing month, the thresholds and the rates live on Amazon's fee page and change by audit or announcement, so cx reads them there. (2026 returns processing fee changes.)
- *Gap fill:* Some return files date a return by when it came back, and others by when the unit shipped. An extended holiday return window moves the season's returns into the weeks after the season in the first kind. It leaves the second kind's figures for the season incomplete until well after the extended deadline. The season and the deadline are re-announced each year and are read from that year's announcement. (FBA Customer Returns report (overview); Seller Analytics Dataset Use Case Guide; Returns and Recovery Insights; Extended Holiday Returns policy.)

## What cx must read at run time

- **FBA returns, row by row:** `createReport` → `getReport` → `getReportDocument` for `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA`. The window, options and waits are door.md's. cx reads the `reason`, `customer-comments` and `detailed-disposition` columns from the file it downloaded, not from memory of a code list.
- **Seller-fulfilled returns:** the same three operations for `GET_FLAT_FILE_RETURNS_DATA_BY_RETURN_DATE` (or the XML, Prime or return-attribute variants). The 60-day span per report and the role are door.md's. Whether the seller's connection carries the role is read from the refusal if there is one.
- **Per-ASIN return rate and return-defect topics:** Data Kiosk `createQuery` → `getQuery` → `getDocument` on `analytics_sellerAnalytics_2025_03_31` (`returns` and `defects` groups, `accountHealth` defect snapshots). The schema is read from the models repository or the dataset guide at run time. Which dates are still incomplete is read from the guide and the schema's field descriptions, which both state the delay. It is not assumed.
- **Per-ASIN refunds:** Data Kiosk on `analytics_salesAndTraffic_2024_04_24`, `salesAndTrafficByAsin` (`unitsRefunded`, `refundRate`). The store-wide line is in `GET_SALES_AND_TRAFFIC_REPORT` `salesByDate`.
- **Category return themes:** Customer Feedback `getItemBrowseNode` (ASIN → browse node), then `getBrowseNodeReturnTopics` and `getBrowseNodeReturnTrends`. For the product's own complaints, `getItemReviewTopics` and `getItemReviewTrends`.
- **Refund money:** Finances `listFinancialEvents` / `listFinancialEventsByOrderId`, `RefundEventList`.
- **Competitors:** Keepa product object `returnRate`: "`null` if the return rate is unavailable or average", "`1` for a low return rate", "`2` for a high return rate" (Keepa's own `Product.java`, github.com/keepacom/api_backend, read 2026-10-14; Keepa's documentation, not Amazon's). This is the only competitor-side return signal on the route. cx reads it from the fetched `product.json`.
- **No API:** VoC, the badge column, Fit Insights, Return Insights thresholds, and Product Opportunity Explorer's Returns tab. cx asks the seller to put a screenshot or export in the tree and reads that file.
- *Gap fill, reconciled:* **Roles. Amazon's own pages disagree, and the binding answer is the authorization error of the first `createQuery`.**
  - On the Role Mappings page, every Data Kiosk operation (`createQuery`, `getQuery`, `getQueries`, `getDocument`, `cancelQuery`) lists Brand Analytics as its only required role. [official] (Role Mappings for SP-API Operations, https://developer-docs.amazon/sp-api/docs/role-mappings, read 2026-10-14, re-read in the reconciliation.)
  - Amazon's changelog says otherwise for one dataset: "The Vendor Analytics and Sales and Traffic datasets require the Brand Analytics role. The Economics dataset requires the Selling Partner Insights role." [official] (Correction: Data Kiosk role requirements, https://developer-docs.amazon/sp-api/changelog/correction-data-kiosk-role-requirements, read 2026-10-14.) The economics dataset is where the returns-fee charges sit (below).
  - The seller analytics dataset (`returns`, `defects`, `accountHealth`) is named in neither page. The guide says only "Access to the seller analytics dataset is governed by the role assigned to your application" and names the "Sales and traffic access" level. The schema gates `returns` and `defects` with the PAAM right `analytics_sales_and_traffic_view_pa`. No Amazon page read maps that right to an SP-API role. [official] (Seller Analytics Dataset Use Case Guide; analytics_sellerAnalytics_2025_03_31.graphql; both re-read 2026-10-14.)
  - The Customer Feedback operations accept Brand Analytics or Selling Partner Insights ("any one of them grants you access"). [official] (Role Mappings for SP-API Operations.)
  - For human readers: Brand Analytics is the role the Role Mappings page lists for the Data Kiosk operations. cx names the role a source needs from the refusal it receives, never from this file.
- *Gap fill:* **Structured comments.** Whether `customer-comments` in the downloaded `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA` file carries the "Base Issue | Issue Detail | Product or Listing Insight" form is read from the file. Amazon says some marketplaces "will continue to display direct customer-provided text".
- *Gap fill:* **Badge state, badge rates, suggested rate, the per-product fee detail and the "Frequently Kept" value:** Seller Central only (Returns and Recovery Insights, Voice of the Customer). cx asks the seller for the export or screenshot and records its date. These figures are not derived from the returns report: the badge's rate excludes non-seller-fault returns and is monthly.
- *Gap fill:* **Returns processing fee:** the thresholds and rate card are read from Amazon's fee page on the day (GZGEQLTM3RZXUV6T at the time of reading). The charges come from Finances (v0 `listFinancialEvents`, or `listTransactions` in `finances_2024-06-19`, not checked here for a returns-fee type) and from Data Kiosk `analytics_economics_2024_03_15` (`economics` → `fees`, and the `HIGH_RETURN_RATE_FEE` / `RETURN_PROCESSING_FEE` preview fee types in `economicsPreview`). Which `feeTypeName` appears is read from the first document. The economics dataset needs Selling Partner Insights according to Amazon's changelog, while Role Mappings lists Brand Analytics for every Data Kiosk operation (see Roles above). Whether the seller's connection can read it is settled by the first `createQuery`'s answer.

## Positions

1. **P-returns-1.** Treat a rise in returns, or a concentration of return reasons on one ASIN, as a trigger that points at the conversion stage's honesty. Read the reasons and comments before proposing any listing change, and never propose a returns fix without them. (How to manage Amazon customer returns for seller-fulfilled orders; Voice of the Customer: A Seller's Guide; Fulfillment by Amazon (FBA) Reports.)
2. **P-returns-2.** Split return reasons into those a listing can address (not as described, not compatible, size or fit, ordered the wrong variant) and those it cannot (defects, damage in transit or at the warehouse, wrong item sent, late delivery, changed mind). Propose a listing change only for the first kind, and treat "quality not as expected" as undecided until comments or reviews say which kind it is. (How to manage Amazon customer returns for seller-fulfilled orders; Reduce apparel and shoe returns with Fit Insights tool; Voice of the Customer - New Amazon Metric; Why do customers return products?; Gorilla ROI and eComEngine as opinion.)
3. **P-returns-3.** Read FBA returns from `GET_FBA_FULFILLMENT_CUSTOMER_RETURNS_DATA` and seller-fulfilled returns from the returns reports by return date. Neither contains the other, and returnless refunds appear in neither seller-fulfilled report. (Fulfillment by Amazon (FBA) Reports; Returns Reports.)
4. **P-returns-4.** Take an ASIN's return rate from the Data Kiosk seller analytics `returns` group, which is dated by ship date. Treat the most recent period that the dataset guide calls incomplete as missing, never as a low rate. (Seller Analytics Dataset Use Case Guide; analytics_sellerAnalytics_2025_03_31 schema.)
5. **P-returns-5.** Do not read the store-wide `refundRate` of the Sales and Traffic report as one ASIN's return rate. For a per-ASIN refund figure use the Data Kiosk Sales and Traffic dataset, and say which of refund or return is meant. (sellerSalesAndTrafficReport schema; analytics_salesAndTraffic_2024_04_24 schema.)
6. **P-returns-6.** When a change targets returns, the change log records the reason distribution and return rate of the baseline, the claim added or corrected, and the reason it is expected to move. The observation window closes only after the return window and Amazon's stated data lag have passed for orders shipped in it. (Seller Analytics Dataset Use Case Guide; How to manage Amazon customer returns for seller-fulfilled orders.)
7. **P-returns-7.** Judge a returns-targeted change on the targeted reason's share and on orders together. A clearer listing can lower conversion while lowering returns, and the verdict is about units kept. Say "cannot tell" when the windows straddle a holiday extended-return period or the badge appeared or cleared mid-window. (Returns window for holiday sales extended to January 31; Track and prevent product return badges; De, Hu & Rahman 2013; Petersen & Kumar 2009.)
8. **P-returns-8.** Use the Customer Feedback API's browse-node return topics as the category's baseline of why buyers return. They describe the category, not the seller's ASIN, and the ASIN's own evidence is its returns report and review topics. (Customer Feedback API; customerFeedback_2024-06-01 model.)
9. **P-returns-9.** The frequently-returned badge, CX Health, the NCX return rate and Fit Insights are Seller Central pages with no API found. cx asks the seller for a screenshot or export into the tree when a review needs them, and does not guess their state. (Track and prevent product return badges; Voice of the Customer: A Seller's Guide; Reduce apparel and shoe returns with Fit Insights tool.)
10. **P-returns-10.** The badge and CX Health are relative to similar products in the category. A rate is "high" only against Amazon's category comparison or its suggested rate, never against an average cx assumes. (Frequently returned item; NCX rate; Track product performance and view translated customer feedback.)
11. **P-returns-11.** When returns are high, state the returns processing fee as a cost consequence, and point to the seller's Return Insights dashboard and Amazon's fee page for the threshold. Note that apparel and shoes are charged under their own returns processing fees, not the high-return-rate threshold. (Update to US referral and Fulfillment by Amazon fees; Updates to the Return Insights dashboard and Returns Processing Fee reminder.)
12. **P-returns-12.** For competitors, read the Keepa product's `returnRate` flag as the only return signal on the route, and say that `null` means unavailable or average. (Keepa `Product.java`.)
13. **P-returns-13.** A return reason is the label the customer picked. Read the free-text comment and the product's review topics next to it before naming a cause. (Why do customers return products?; View insights on your FBA returns; Customer Feedback API.)
14. **P-returns-14.** When the FBA returns file carries Amazon's structured comment, use its Listing Insight part as the first evidence that copy caused a return. Amazon applies it to wrong-item, missing-parts, not-as-expected, too-large, too-small and size/fit returns, and treats not-compatible returns under Product Insight. Where the comment is free text, cx reads the text itself. (FBA Customer Returns report (overview); FBA Returns page.)
15. **P-returns-15.** Never treat a `NOT_AS_DESCRIBED` or size code as proof by itself: Amazon says the buyer picks the reason from a standard list and it "may not always accurately reflect the true return circumstances". Name a listing cause only when comments, Listing Insight or review topics agree. (FBA customer returns policy; FBA Customer Returns report (overview).)
16. **P-returns-16.** cx never infers badge status, the badge rate or distance to the suggested rate from the returns report or from Data Kiosk. The badge rate counts only returns attributable to the seller, is refreshed monthly, and its suggested rate changes over time. cx reads the seller's Returns and Recovery Insights or Voice of the Customer export and records its date. (Returns and Recovery Insights; Frequently returned item badge.)
17. **P-returns-17.** A change log for a badged ASIN does not promise a removal date. Amazon removes the badge as the rate approaches the suggested rate, may remove it earlier on a consistent downward trend, and publishes no recovery period. The effect review records the badge state at the start and at the end of the window. (Frequently returned item badge; Returns and Recovery Insights.)
18. **P-returns-18.** When cx quotes a return rate, it names which one: the overall rate (Returns and Recovery Insights, Data Kiosk `returnedRate`), the fee rate (physical returns over the measurement window the fee page states), the badge rate, or the NCX return rate (orders with a product or listing issue over total orders). It never compares one kind against another. (Returns and Recovery Insights; 2026 returns processing fee changes; Voice of the Customer; Seller Analytics Dataset Use Case Guide.)
19. **P-returns-19.** For the returns processing fee, cx names the mechanism, not a figure. Apparel and shoes pay on every returned unit. All other products pay only on returned units above their category threshold, billed after a measurement window that runs past the ship month. The window, the billing month, the thresholds and the rates are read from Amazon's fee page on the day. (2026 returns processing fee changes; Update to US referral and Fulfillment by Amazon fees.)
20. **P-returns-20.** cx counts returnless refunds as returns for rate purposes but notes that they leave no row in the FBA returns report. A reason distribution from that file is therefore a sample of physical returns only. (FBA Customer Returns report (overview); FBA Returnless Resolutions; Returns and Recovery Insights.)
21. **P-returns-21.** In an effect review, cx compares return figures only on the same dating basis (return or processing date against return date, ship date against ship date). It treats a rise in a return-dated file just after the holiday season as possibly the season's sales coming back under the extended return window. A window that includes shipments covered by that extended window stays open for returns until the year's extended return deadline and Amazon's stated data delay have both passed. The season, the deadline and the delay are read from the year's announcement and the dataset guide, not from this file. (FBA Customer Returns report (overview); Returns Reports; Seller Analytics Dataset Use Case Guide; Returns and Recovery Insights; Extended Holiday Returns policy; FBA customer returns policy.)
22. **P-returns-22.** For the seller analytics `returns` and `defects` groups and for the economics returns-fee lines, cx does not assert a role in advance. Amazon's role pages disagree, and the seller analytics schema gates these groups by a PAAM right that no page maps to a role. cx takes the authorization error of the first `createQuery` as Amazon's answer, names the role that error points to, and records the source as unread until access is granted. (Role Mappings for SP-API Operations; Correction: Data Kiosk role requirements; Seller Analytics Dataset Use Case Guide; analytics_sellerAnalytics_2025_03_31 schema.)
