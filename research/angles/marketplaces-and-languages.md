# Marketplaces and languages: what changes outside the US store

Read 2026-10-14 by the research seat. Tags: [official] Amazon's own page or document; [opinion] a named practitioner; [research] published research; [seat] the seat's own reasoning, never a skill position.

How the Seller Central help pages were read. Each `sellercentral.<domain>/help/hub/reference/external/<id>` page is a JavaScript shell. Its body was read through the help hub's own content call (`POST /help/hub/mons-api/GetHelpTopic`, body `guid`, layer `external`, locale `en-US`), the call the page itself makes. That call is undocumented. Sent to a store's own Seller Central host (`sellercentral.amazon.de`, `.co.uk`, `.co.jp`, `.ca`, `.com.mx`, `.ae`, `.sa`, `.eg`, `.com.tr`, `.com.au`, `.in`), it returns that store's **layer** of the page (`Published/DE`, `Published/GB`, `Published/JP` and so on), in English. The layers differ in substance, not only in spelling, and this file depends on that. Each citation names the layer and version read. The US and GB texts this file cites are also saved as captures under the office's capture folder (outside this repository) (G23501 v14 US and v9 GB, G10471 v13, GF2C2L6RCFZGWBXC v4, GYTR6SYGFA5E3EQC v21, G202121570 v14 US and v13 GB, G202121610 v10, G202121580 v6), read 2026-10-14; the quotes below were re-matched against those captures. The DE, JP, CA, MX, AU, IN, AE, SA, EG and TR layers were read by this seat the same day and have no capture there. Whether the content call may stand as a route is for the office to rule (method/help-page-access.md, Open question 1); no further page was fetched through it in the reconciliation pass. Customer-facing amazon.de / .fr / .co.uk help pages were read as plain HTML. SP-API pages were read in their `.md` form at `developer-docs.amazon/sp-api/...`; the `developer-docs.amazon.com` URLs redirect there. The search budget for this session ran out after nine searches. Everything after that was reached by a known URL or by a link inside an Amazon page. No Amazon API host and no Keepa API host was called. No seller data appears here.

## What this covers

- **Funnel stages.** All three, because the store decides the rules for each. Exposure: language-tagged text, search-term byte limits, title length. Click-through: which title and price treatment the shopper sees, such as the EU lowest-price-in-30-days display. Conversion: GPSR safety content on the detail page, the returns promise. This file also covers **none**, the attribution problem: which store a change landed in and which store's series measures it.
- **Skills fed.**
  - *listing-review*: per-store rules, with GPSR and CE/UKCA as mandatory content in EU and UK stores.
  - *listing-change-log*: every entry needs a `marketplace_id`, plus a list of the other stores the change reaches, because images are global and BIL syncs prices.
  - *effect-review*: read the series of the store that was changed, one store per report. Add BIL price moves, EU price displays and EU return windows to the confounders.
- **Why a senior operator cares.** Today's research files are US-first. An operator running US + CA + MX, or US + EU5 + UK, or JP, expects the following to be known:
  - A main-image swap meant for the US also changes DE, UK and JP.
  - A BIL source store's sale price starts a sale in every target store.
  - A listing that is fine in the US can be deactivated in DE for a missing EU Responsible Person.
  - JP counts title characters, not bytes, and allows a different search-term budget.
  - An EU discount is judged against the 30-day low, not the US Was Price.
  - An effect read from the wrong store's report is worthless.

## Amazon's own rules and guidance

### A. Stores, regions and identifiers

A1. **RULE: one marketplace id per store; three regional endpoints.** The Marketplace IDs page: "Each marketplace ID is a unique identifier that represents a specific country where Amazon customers can shop." It lists them by region. North America and Brazil: CA, US, MX, BR. Europe, Middle East, India and Africa: IE, ES, UK, FR, BE, NL, DE, IT, SE, ZA, PL, EG, TR, SA, AE, IN. Far East: SG, AU, JP. The endpoints page says requests go "to the correct endpoint based on your target Amazon store":
- `sellingpartnerapi-na` covers Canada, US, Mexico and Brazil.
- `sellingpartnerapi-eu` covers the European, Middle Eastern and African stores plus India; it includes the UK, Saudi Arabia, Egypt, Turkey and the UAE.
- `sellingpartnerapi-fe` covers Singapore, Australia and Japan.

[official] (Marketplace IDs, https://developer-docs.amazon/sp-api/docs/marketplace-ids.md, updated 2026-09-30; SP-API Endpoints, https://developer-docs.amazon/sp-api/docs/sp-api-endpoints.md, updated 2026-09-09; read 2026-10-14)

A2. **RULE: catalog data differs by store.** "An ASIN represents the same physical item in every Amazon store, with few exceptions. However, the data for each ASIN differs by Amazon store because countries have different data requirements specific to that Amazon store." And: "because most attributes are localized text, the text can differ depending on the Amazon store or locale … Use the `marketplaceIds` filter in the Product Type Definitions API … to get the Amazon store-specific requirements". [official] (Listings APIs FAQ, https://developer-docs.amazon/sp-api/docs/listings-apis-faq.md, updated 2026-09-09, read 2026-10-14)

A3. **RULE: images are global per ASIN, whatever the write says.** "The image attributes provided by the Listings Items API v2021-08-01 operations map images to ASINs at a global level where the ASIN exists, even if you specify the `marketplace_id` selector. This behavior is consistent with other experiences, such as **Add a Product** within Seller Central." [official] (Listings APIs FAQ, "Did my image update apply globally?", read 2026-10-14)

A4. **RULE: writes name their store.** In the Listings Items model, `marketplaceIds` is "A comma-delimited list of Amazon store identifiers for the request." It is limited to one item (`maxItems 1`) for `putListingsItem` and `deleteListingsItem`. No `maxItems` is set for `patchListingsItem`, `getListingsItem` or `searchListingsItems`. Amazon's text examples carry `language_tag` and `marketplace_id` inside each value. In the Submit modular titles sample, these are `"language_tag": "en_US"` and `"marketplace_id": "ATVPDKIKX0DER"`, and the attribute's `selectors` are `marketplace_id` and `language_tag`. [official] (listingsItems_2021-08-01.json, https://github.com/amzn/selling-partner-api-models/blob/main/models/listings-items-api-model/listingsItems_2021-08-01.json; Submit modular titles, https://developer-docs.amazon/sp-api/docs/submit-modular-titles.md, updated 2026-09-10; read 2026-10-14)

A5. **RULE: the seller sales-and-traffic report is one store per report.** In the schema, `marketplaceIds` "must match the marketplaceId of the seller's account. This report type supports only one marketplaceId per report. Specifying multiple marketplaces will result in failure to generate the report." [official] (sellerSalesAndTrafficReport.json, https://github.com/amzn/selling-partner-api-models/blob/main/schemas/reports/sellerSalesAndTrafficReport.json, read 2026-10-14) The Analytics Reports page shows the same one-store constraint elsewhere. Its vendor forecasting example error reads "There were 9 marketplaces in the request, but only 1 is supported." For the vendor retail reports, the store data "follows PST irrespective of the vendor's location or the Amazon store's local time zone". That sentence is about vendor reports; the page gives no seller-report time zone. [official] (Analytics Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-analytics.md, read 2026-10-14)

### B. Language tags and the locale of a value

B1. **What Amazon's own documents show.** No Amazon page read lists the `language_tag` values allowed per store. That list lives in each product type schema's `$defs.language_tag`, fetched with `getDefinitionsProductType` for one `marketplaceIds` value ("This parameter is limited to one marketplaceId at this time"). The Amazon documents read do show the following.
- The `locale` parameter of `getDefinitionsProductType`, which controls display labels, takes this enum: `DEFAULT, ar, ar_AE, de, de_DE, en, en_AE, en_AU, en_CA, en_GB, en_IN, en_SG, en_US, es, es_ES, es_MX, es_US, fr, fr_CA, fr_FR, it, it_IT, ja, ja_JP, nl, nl_NL, pl, pl_PL, pt, pt_BR, pt_PT, sv, sv_SE, tr, tr_TR, zh, zh_CN, zh_TW`. This is the display-label locale, not the value's `language_tag`, but it shows the vocabulary: underscore form, with `es_US`, `fr_CA` and `ja_JP` among the values. [official] (definitionsProductTypes_2020-09-01.json, https://github.com/amzn/selling-partner-api-models/blob/main/models/product-type-definitions-api-model/definitionsProductTypes_2020-09-01.json, read 2026-10-14)
- `issueLocale` on every Listings Items operation: "Examples: `en_US`, `fr_CA`, `fr_FR`. Localized messages default to `en_US` when localization is not available". [official] (listingsItems_2021-08-01.json, read 2026-10-14)
- The GPSR help page on compliance documents gives Amazon's own per-store language codes: "the code for the official language of the store … (for example, fr_FR for France or fr_BE for Belgium). If you're uploading a multilingual document, select the official language of the store only." [official] (Submitting manufacturer, Responsible Person, and warning and safety information, G8AECGHY2KLD88D7, layer Published/DE v15, https://sellercentral.amazon.de/help/hub/reference/external/G8AECGHY2KLD88D7, read 2026-10-14)

B2. **Belgium: one listing language, machine-translated into the others.** "Important: note that you have to list your products in French. It will be automatically translated in Dutch and English." [official] (Selling on Amazon.com.be, Getting Started Guide, Amazon Services Europe, 2023 (PDF created 2023-08-03), https://m.media-amazon.com/images/G/51/selleruniversity/Getting_Started_Guide_BE-en_2023.pdf, read 2026-10-14) This is a 2023 guide; no current help page on BE listing language was read.

B3. **[copy] What live schemas look like.** These are third-party copies of Amazon schema documents, not Amazon pages. Each copy's `$id` is `https://schemas.amazon.com/selling-partners/definitions/product-types/schema/v1/<TYPE>`.
- Amazon.de `PRODUCT` copy (committed 2024-11-14). `$defs.language_tag` has default `de_DE` and enum `cs_CZ, nl_NL, en_GB, de_DE, pl_PL, es_ES, es_US, tr_TR`, so one store's schema accepts text in several languages. `generic_keyword` has `maxUtf8ByteLength` 250. (germanbisurgi/jedison, `src-docs/json/examples/amazon.json`)
- Amazon.es `PRODUCT` copy (default and only enum value `es_ES`) and Amazon.com.au `AUTO_PART` copy (`en_AU`), both committed 2025-08-05. `generic_keyword` has `maxUtf8ByteLength` 2000 and `maxLength` 500; `item_name` has `maxLength` 200. (ztao0916/demo-js, `schemajson/json/es.json`, `au.json`) Both copies predate the 2026 title rule (D1, D3), so their 200 says nothing about today's schema; the figures in these copies are for human readers, and the binding values are those `getDefinitionsProductType` returns for the store and product type at run time.
- In all three copies `language_tag` is declared as `anyOf: [{type: string}, {type: string, enum: [...]}]`. Read literally under JSON Schema, any string satisfies the first branch. Whether Amazon's validator rejects a tag outside the enum cannot be told from the copy (Open questions).
- Read 2026-10-14 at https://github.com/germanbisurgi/jedison/blob/main/src-docs/json/examples/amazon.json and https://github.com/ztao0916/demo-js/tree/main/schemajson/json.

B4. **Run finding (internal).** The day-2 run's drafted patch body wrote `"languageTag": "en-US"` and carried no `marketplace_id` in the value. Amazon's documented form is snake_case `language_tag` with an underscore locale, `en_US`, next to `marketplace_id` (A4). The same draft also replaced `main_image_url`, which would have reached every store where the ASIN exists (A3). (20261014-0921-beta-browser-listing-run-day-2.md, read-only)

### C. Build International Listings (BIL), unified accounts and linked accounts

C1. **What BIL does (RULE: the tool's behaviour).** "The Build International Listings tool helps you create and update offers from a single source store to one or more target stores … From that source store, the tool will update eligible offers and prices in the target stores based on settings that you specify and the currency exchange rates." It "works within a region where there are multiple stores, such as Europe or North America, and across regions when you have connected them by linking accounts." Its automated tasks, verbatim:
- "Creates offers from a source store to a target store where the same ASINs already exist in both stores."
- "Synchronizes the offer prices in target stores based on the price you set in the source store and your price rules."
- "Adjusts prices periodically to reflect currency conversion fluctuations in the target stores' currencies. The frequency of these updates may vary from daily to weekly. These updates will not show changes of less than 1%."
- "Adds or deletes offers in the target stores when you make changes to eligible ASINs in the source store."
- "Attempts to translate and create product detail pages in a target store."

Under "does not", the page says BIL does not "Guarantee the creation of new product detail pages". It also does not "Remove offers in the target store when the offer becomes inactive in the source store" or "Check that your products comply with applicable laws and regulations across all stores". On creating pages: "If a product detail page with the same ASIN does not exist in the source and target stores, Amazon will attempt to translate and create the product detail page in the target stores. Amazon does not guarantee the creation of a product detail page." Its requirements are a Professional account, a "European Unified Account" for Europe, a "North America Unified Account" for North America, and "Linked accounts between regions" across regions. Inactive connections: Amazon "will delete connections that have not synced new listings from your source store or generated any sales in your target stores in the past 12 months". [official] (Build International Listings, G202121570, layer Published/US v14; the Published/DE layer v14 and the Published/GB layer v13 say the same, with "such as in the EU or North America", https://sellercentral.amazon.com/help/hub/reference/external/G202121570, read 2026-10-14; US and GB captures under the office's capture folder (outside this repository))

C2. **Price sync detail (RULE).**
- "A sale price in the source store will initiate a sale in the target store. The sale price is synchronized only during the defined sale period."
- "Store price rules apply to your entire inventory for the combination of target store and fulfillment method. Store price rules cannot be set for individual ASINs or SKUs."
- "If you make a manual change to your ASIN price in your target store or stores, the connection to your US price will be broken".
- After a price-rule update: "It may take up to four hours before the price changes are reflected in each target store."
- "If you change the price of an offer that is inactive in the source store, the price will be updated in the target store."

[official] (Build International Listings price rules, G202121610, Published/US v10, read 2026-10-14)

C3. **Editing in a target store breaks the link (RULE).** "Change your offers only in the source marketplace … If you make any change in the target marketplace — for example, if you change the price of an offer or delete an offer — the connection for the offer between the marketplaces will be broken. When a connection is broken, it will have the same effect as when you exclude the SKU." Exclusion is "at the SKU level", per target store; at most "1,000 SKUs can be excluded at a time". An excluded offer stays active, but its price is no longer synchronized or adjusted for exchange rates. [official] (Exclude offers or products from a target marketplace, G202121630, Published/US v1, read 2026-10-14)

C4. **Choosing targets can destroy history (RULE).** "If you delete existing offers, all offers, histories, and reviews will be deleted … You cannot undo this action." Also: "Target marketplace prices for connected offers will update automatically whenever you change your source marketplace prices." [official] (Choose your source and target marketplaces, G202121600, Published/US v1, read 2026-10-14)

C5. **Where the sync is visible.** The BIL Status report has "Synchronization Date", "Product Name (Source Store)", "Product Name (Target Store)" ("The product name in the target store language"), the target list price, currency and sale price, and "Synchronization Status" with reasons. It is generated from the BIL page ("Click Generate report"), not named as an SP-API report type on any page read. [official] (Build International Listings report, G202121620, Published/US v10, read 2026-10-14) The Global Offer Manager dashboard shows translation status: "If any of your products are already in the translation queue, you will see an In progress indicator. If Amazon is not translating product detail pages for you, you will need to create the detail pages yourself." [official] (Global Offer Manager, GMF7RM22XQ3FMWA5, Published/US v1, read 2026-10-14)

C6. **What BIL translates.** The answer depends on the source, and none of them settles whether BIL keeps a translation in step with the source after the page exists.
- Amazon's help pages say only "Attempts to translate and create product detail pages" (C1).
- Amazon's Seller University deck "How to Upload Listings and Evaluate Listing Quality" (CN_GS_Listing_Basics_1.4, PDF dated 2024-03-31) compares List on One, Sell Globally (LOSG) and BIL. The extracted layout does not show whether that cell belongs to LOSG, BIL or both. The A+ row reads "Sync A+ Content; automatic translation currently only works for product descriptions within a single region (such as the US to Mexico, or within the European Union)". [official] (https://m.media-amazon.com/images/G/28/AS/AGS/SU/CN_GS_Listing_Basics_1.4_Uploading_EN.pdf, read 2026-10-14)

[official] (https://sell.amazon.com/blog/amazon-listing-translation, read 2026-10-14)

### D. Title length outside the US, and the exempt stores

D1. **RULE, as stated in the US, EU, GB, JP, CA, MX, AU and IN layers (all version 21).** "Title requirements apply to all product types, except media product types, listed in all stores, except for Saudi Arabia, Egypt, Türkiye, and the United Arab Emirates." "Titles must not exceed 75 characters, including spaces." The note "allow 24 to 48 hours for updates to be processed and displayed on Amazon stores" is present in these layers; the US layer words it "Allow 24 to 48 hours for the change to be processed and displayed on search results and the product detail page" and, in its FAQ, "the change is accepted immediately but can take 24 to 48 hours to be processed and displayed on Amazon stores, including search results and the product detail page". That is a display time for title and Item highlights changes, not an effect window. For a title already listed, the US layer says: "If your product is already listed and the title doesn't comply with these requirements or contains inaccurate information, the title might be automatically corrected or it might not appear in our search results." Its Item highlights FAQ: "Item highlights provide an additional 125 characters". [official] (Product title requirements and guidelines, GYTR6SYGFA5E3EQC, layers Published/US, DE, GB, JP, CA, MX, AU, IN v21, read 2026-10-14; US capture capture `GYTR6SYGFA5E3EQC-v21`)

D1a. **Amazon's own sources disagree on the title length a write may carry.** The title page says 75 characters. Amazon's SP-API pages give 200 for `item_name`: the Listings Items API Issues Troubleshooting page's `90225` example reads "item_name : 200 characters" (as quoted in method/listing-writes.md and elements/search-terms.md), and Submit modular titles says "If you submit an `item_name` longer than 75 characters (up to 200), Amazon may reconcile the value in the catalog, splitting it across `item_name` and `title_differentiation`" (as quoted in elements/title.md). The ES and AU schema copies (B3) carry `maxLength` 200. Both figures are for human readers. The binding value for a store and product type is read at run time from `getDefinitionsProductType` (`item_name` `maxLength`, and whether `title_differentiation` exists), together with the `issues` a `VALIDATION_PREVIEW` returns.

D2. **The exempt stores' own layers contradict the exemption.** The Published/AE, SA, EG and TR layers (also v21) say instead "Title requirements apply to all product types, except media product types, in all of our worldwide stores." They keep "Titles must not exceed 75 characters, including spaces" in the requirements table. Their best-practice table says "200 or fewer characters is required because mobile screens truncate long titles", where the US layer says "75 or fewer". They have no Item highlights paragraph and no "24 to 48 hours" sentence. [official] (same page, layers AE, SA, EG, TR, read 2026-10-14) So Amazon's own pages disagree on whether a 75-character limit binds in SA, EG, TR and AE. The schema for that store and product type settles it (`item_name` `maxLength`, and whether `title_differentiation` exists).

D3. **The 2026 rewrite announcement names no store.** "Starting July 27, 2026, titles in all categories except for media will need to be 75 characters or less including spaces." Titles still over the limit "will be updated to the AI recommendation gradually". The post names no store or marketplace. [official] (Updates to improve your product titles begin on July 27, News_Amazon, Jun 10, 2026, https://sellercentral.amazon.com/seller-forums/discussions/t/145b6d0f-999c-4555-896c-c694bda2e470, read 2026-10-14) It was read on the US forum only, and no EU, UK or JP forum copy was read.

### E. Japan

E1. **RULE: title and Item highlights limits count characters, not bytes.** From the JP-only FAQ entry: "Amazon's title policy limit (for both product title and item highlights) is character-based, not byte-based … a 75-character string is 75 characters in any language … a character will be counted as singular irrespective of its size, for both the 75-character limit in titles and 125-character limit in item highlights." [official] (Product title requirements and guidelines, Published/JP v21, https://sellercentral.amazon.co.jp/help/hub/reference/external/GYTR6SYGFA5E3EQC, read 2026-10-14)

E2. **RULE: JP-only title content rules.** "For free trial versions such as subscription products, indicate the specific number of days, such as "30-day free trial version" in the product title." Products with a limited purchase period must "give the specific period of time in the product title". [official] (same, Published/JP)

E3. **RULE: search terms are measured in bytes, and the JP budget differs from the other stores, though Amazon's JP pages disagree with each other.**
- "Use search terms effectively", Published/JP v14: "Amazon limits the length of the Search Terms attribute to less than 500 bytes (less than 250 bytes for Fashion category)." "Optimize your product discoverability", Published/JP v13: "less than 500 bytes".
- "Keyword attributes explained", Published/JP v4: "Search Terms (generic_keywords) should be less than 250 bytes long … If it exceeds the limit, the attribute is completely ignored by Amazon Search."
- The JP layer of G10471 also adds ranking factors absent from the US layer: "degree of match of text and other information, price, Amazon Points, availability, selection, sales history, and suspected violation of applicable laws or policies".

[official] (G23501, G10471, GF2C2L6RCFZGWBXC, Published/JP, https://sellercentral.amazon.co.jp/help/hub/reference/external/<id>, read 2026-10-14)

E4. **Spaces.** In the US, JP, GB and DE layers of G23501: "No. For the purpose of calculating the length of search terms, Amazon search does not count spaces or punctuation." In the JP, GB and DE layers: "If Search Terms are over the limit, none of the Search Terms for that ASIN will be indexed by Amazon Search." The US layer (v14) has no such over-limit answer; the US "Keyword attributes explained" (v4) says instead "If it exceeds the limit, the attribute is completely ignored by Amazon Search." [official] (G23501, Published/US v14, Published/JP v14, Published/GB v9, Published/DE v14; GF2C2L6RCFZGWBXC Published/US v4; read 2026-10-14; US and GB captures under the office's capture folder (outside this repository)) The GB answer was "Yes, Amazon search counts spaces and punctuations" in a 2022 archived copy cited by elements/search-terms.md. The current GB layer says no. These sentences are about how Amazon search measures the indexed terms. elements/search-terms.md records that the write-side validator counts every byte of the value as sent, spaces included; the two counts are different things.

### F. Search-term budget by store (other than JP)

F1. "Use search terms effectively" Published/GB v9 and Published/DE v14: "Amazon limits the length of the Search Terms attribute to less than 250 bytes." The GB and DE layers of "Optimize your product discoverability" say "less than 250 bytes". The US layer of G23501 (v14) no longer states a figure in its body; it says only "the Generic keyword field in Seller Central stops accepting inputs when the byte limit is reached". Two other US pages do state one, and not the same one: "Optimize your product discoverability" (G10471, Published/US v13): "We limit the length of the Generic Keyword attribute to less than 250 bytes"; "Keyword attributes explained" (GF2C2L6RCFZGWBXC, Published/US v4): the table's "Length Limit (Bytes)" for `generic_keywords` is "249", and its text says "should be less than 250 bytes long". [official] (G23501, G10471, GF2C2L6RCFZGWBXC per layer, read 2026-10-14; US and GB captures under the office's capture folder (outside this repository))

F2. **Amazon's pages and the schema disagree on the search-term limit.** The help pages give under 250 or 249 bytes (US, GB, DE; JP's "Keyword attributes explained") and under 500 bytes (JP's G23501 and G10471, with 250 for Fashion). Amazon's Listings Items API Issues Troubleshooting page lists "`generic_keyword`: 500 bytes" as its `90225` example (as quoted in elements/search-terms.md and method/listing-writes.md). The schema copies in B3 give `maxUtf8ByteLength` 250 (DE) and 2000 with `maxLength` 500 (ES, AU). These figures are for human readers. The binding write limit for a store and product type is read at run time from `getDefinitionsProductType` (`generic_keyword` `items.properties.value.maxUtf8ByteLength` and `maxLength`), and a `VALIDATION_PREVIEW` names it in a `90225` issue. The help pages' lower figures are about what search indexes, which the schema does not state; a write that passes the schema can still be over the indexing limit the store's help page states.

### G. EU and UK product-safety content (GPSR, Responsible Person, CE / UKCA)

G1. **RULE: GPSR scope and enforcement.** "Effective December 13, 2024, the General Product Safety Regulation (GPSR) sets out requirements for most non-food consumer products offered for sale in the EU." The page lists exemptions, for example medicinal products, food and beverages, animal feed, living plants and animals, plant protection products and antiques. Enforcement: "All listings in scope of the GPSR must be compliant with the requirements, and we deactivate them if we become aware of non-compliance". This covers cases where information "has been submitted, but we find it to be invalid, or the contract with the service provider acting as the Responsible Person has ended". Existing listing errors come first: "existing issues prevent listings from being reactivated, even if you've fulfilled all compliance requirements." [official] (General Product Safety Regulation (GPSR), GQAYBJPNAZ2LMDDT, Published/DE v15, https://sellercentral.amazon.de/help/hub/reference/external/GQAYBJPNAZ2LMDDT, read 2026-10-14)

G2. **RULE: what must be on the detail page.**
- **Manufacturer.** "you must display the manufacturer's name and contact information on the product detail page"; "your manufacturer can be based in any country".
- **Responsible Person.** "there must be an EU-based Responsible Person for your products". The Responsible Person may be the manufacturer or brand, the importer, an authorized representative, or a fulfillment service provider, "if established in the EU or Northern Ireland". Their name and contact information must be displayed on the detail page.
- **Warnings.** "you must label your products with the required warning and safety information and display it on the product detail page, in the language of the country of sale". This can be done with images, documents, or "a safety attestation (this option is only available for certain products)".
- **Languages.** Images and documents must be "in the official languages of the country for that store", either monolingual or covering "all the official languages of the country".

Where it shows: "Information provided for the GPSR is displayed in the "Safety and Product Resources" section of the product detail page." Display rules: "We display one manufacturer submission per ASIN"; "We display all Responsible Person submissions". [official] (GPSR, Published/DE v15, read 2026-10-14)

G3. **RULE: the listing attributes.**
- New listings: "You must submit the required GPSR information when you create your listing … for each store." The attributes are "Safety Attestation" ("If you choose this option, but the product does require warning and safety information, your listing will not be created"), "Compliance media language", "Compliance media content type" and "Compliance media source location" ("a direct download link").
- Manufacturer and Responsible Person contacts go in through Account Health → Regulatory Compliance for brand-registered products, or through "Review blocked reason" → "Fix listing" for unbranded ones. Compliance checks "can take between 2 and 48 hours"; valid information makes a listing active "within seven days".
- GPSR images use dedicated variants: "you must use the PS01-PS06 variants". These "may be removed if they are in the wrong language or aren't readable".

[official] (Submitting manufacturer, Responsible Person, and warning and safety information, G8AECGHY2KLD88D7, Published/DE v15, read 2026-10-14)

The SP-API change note names the attributes:
- `gpsr_manufacturer_reference.gpsr_manufacturer_email_address`, described as ASIN level;
- `dsa_responsible_party_address`, described as SKU level;
- `gpsr_safety_attestation`;
- `compliance_media`, with `content_type`, `content_language` and `source_location`.

It names the stores (ES, FR, BE, NL, DE, IT, SE, PL). It says sellers must first enter manufacturer and Responsible Person contacts in Seller or Vendor Central, and that schemas come from `getDefinitionsProductType`. [official] (Update: Support for GPSR compliance in Listings Items API and JSON Listings Feeds, https://developer-docs.amazon/sp-api/changelog/developers-can-use-attributes-in-their-programmatic-listings-submissions-to-comply-with-gpsr, no publication date shown, read 2026-10-14) In the ES and AU schema copies (B3), these four attributes carry `selectors` keyed by `marketplace_id`, and `compliance_media` adds `content_type` and `content_language`. Unlike images, they are per store. [copy]

G4. **RULE: CE-marked goods and the Market Surveillance Regulation.** "This regulation requires CE-marked products to have a person or company established in the European Union acting as the point of contact for product compliance (a "Responsible Person")." Since July 16, 2021, "sellers based outside the EU who use Fulfillment by Amazon (FBA), must submit the Responsible Person information for their CE-marked products to Amazon, to avoid listing removal." [official] (Market Surveillance Regulation, GSDP2QRYVQ5SUFLE, Published/DE v15, read 2026-10-14)

G5. **RULE / GUIDANCE: CE, UKCA and UKNI.**
- The page opens: "The UK government has released guidance stating that for all products apart from medical devices, CE marking will be accepted in the UK indefinitely."
- Great Britain: "The CE and UKCA marks are accepted for imports into Great Britain."
- EEA: "Products with a UKCA mark must also have a CE mark if they are sold in the EEA."

- Testing: "All CE-marked products must be tested. To list a CE-marked product in Amazon Stores, you must use one of our authorised third-party testing, inspection and certification (TIC) service providers … to obtain a test report, or approve an existing one."

[official] (EU and UK product marking guidance: CE and UKCA marking, G3NRFVS4YUYRQ85J, Published/GB v11, https://sellercentral.amazon.co.uk/help/hub/reference/external/G3NRFVS4YUYRQ85J, read 2026-10-14)

Amazon's UK marketing hub words it differently: "Products must meet UKCA (Great Britain) or CE (Northern Ireland) marking requirements", and "If selling CE-marked goods, you are legally required to appoint a Responsible Person (RP) based in the UK or EU." [official, marketing page] (Compliance Hub - Selling Partner's Guide | Amazon UK, https://sell.amazon.co.uk/selling-partner-compliance-hub, read 2026-10-14) The help page (both marks accepted in GB) is the more specific and newer-looking text. ### H. EU price display: the 30-day prior price

H1. **RULE (customer-facing, France).** "For price reduction announcements, such as limited-time promotions, we display the lowest recent price of the product on Amazon.fr in the last 30 days before the price reduction is applied." On amazon.fr an RRP displays only if the price "was equal to or higher than the RRP in the last 90 days". [official] (Reference Pricing and Savings, Amazon.fr customer help, https://www.amazon.fr/gp/help/customer/display.html?nodeId=GQ6B6RH72AX8D2TD&language=en_GB, read 2026-10-14)

H2. **UK and DE customer pages.** The UK page: "Lowest price in 30 Days means that the current price is lower than, or equal to, the lowest featured offer price for this item sold on Amazon.co.uk in the past 30 days". Its Was Price is the median paid "in the last 90 days". The DE page defines RRP, One-Time Price, Was Price (median, "excluding promotional prices") and New Price. It contains no 30-day sentence like amazon.fr's. [official] (Reference Pricing and Savings, amazon.co.uk and amazon.de customer help, same nodeId, read 2026-10-14) [seat] The DE page as served today does not state how DE shows the Omnibus prior price. That is a gap in the page, not evidence of no display.

H3. **RULE (seller side, EU layer): minimum discounts measured against the 30-day low.** The Price discounts page, Published/DE v8, lists these criteria.
- Prime-exclusive discounts:
  - "at least 5% off the lowest price excluding promotions in the last 30 days in the UK, Germany, and the Netherlands";
  - "at least 2.5% off the lowest price in the last 30 days in France, Spain, Belgium, Poland, and Italy and 5% off in Sweden".
- Non-Prime discounts: "at least 5% off the lowest price excluding promotions in the last 30 days".
- Durations: "between 1 to 30 consecutive days".
- Rating: "Products must have at least a 3.5-star rating".
- Display: "Products without a validated reference price don't display a strike-through price or savings to customers."

[official] (Price discounts, G7F8CQ4EJ5YA4272, Published/DE v8, https://sellercentral.amazon.de/help/hub/reference/external/G7F8CQ4EJ5YA4272, read 2026-10-14) These figures are Amazon's and change by event ("The criteria may change for particular events"). They are for human readers.

H4. **RULE: discount duration in Europe.** "Your discounts must respect any legal minimum and maximum durations. For some of our European stores, this is a maximum of 30 calendar days." The DE layer defines the Was Price as "determined using historic prices paid by customers for the product on Amazon store, excluding promotional prices". [official] (Amazon policy on reference prices, G202170370, Published/DE v19, read 2026-10-14)

## What practitioners add

- **eComEngine (Vanessa Hester), "How to Set Up Amazon's Build International Listings Tool", published and updated July 27, 2023.** The tool "will not create new product listings for you" and "does not automatically set up your inventory". Changing the fulfillment method in a target store means that store "will no longer automatically mirror the offer at the source marketplace". Exclusions are the way out. On this point the post disagrees with Amazon's current page, which says BIL "attempts to translate and create product detail pages". The post is about offers on ASINs that already exist. [opinion] (https://www.ecomengine.com/blog/build-international-listings-amazon, read 2026-10-14)
- **My Amazon Guy, "Why Bilingual Product Listings on Amazon Canada Are Non-Negotiable for Sellers", modified August 20, 2026, author not stated.** It claims Amazon.ca expects a single bilingual listing: title, bullets, description, A+ and backend terms in both languages. It warns that separate English and French ASINs for the same product "can violate policy". It names Quebec's Bill 96 (Charter of the French Language). No Amazon page read here states a bilingual requirement for Amazon.ca, so this stays opinion. The article itself is inconsistent: its body calls duplicates a violation and its FAQ says they "can" be. [opinion] (https://myamazonguy.com/amazon-canada/bilingual-product-listings-on-amazon-canada/, read 2026-10-14)
- **Marketplace Valet (agency led by Will Land, Laura Land and Justin Boggs), service page, undated (© 2026).** It advertises backend search terms "fully optimized with misspellings, Spanish translations, and long-tail variations". Spanish terms in US backend keywords are a practitioner habit. The current US layer of G23501 says nothing about other-language terms. The same page advises "don't include common misspellings", so the agency and Amazon disagree on misspellings. [opinion] (https://marketplacevalet.com/mastering-amazon-listing-translations-for-international-markets/, read 2026-10-14)
- **Seller Forums (sellers, not staff).** On the thread about the English rendering of a German listing, one seller reports editing the UK translation while "the English version of the German one is randomly different". On "Build international listings manually" (sellercentral-europe, about five years old), a seller quotes Amazon's note "Amazon translates certain ASIN detail pages automatically" and "If your page is not in the queue for translation, you can use Amazon's Add a Product tool to create the page manually". ## Published research

- **Brynjolfsson, E., Hui, X., Liu, M., "Does Machine Translation Affect International Trade? Evidence from a Large Digital Platform", Management Science 65(12):5449–5460, 2019 (NBER WP 24917, August 2018).** On eBay, the introduction of a machine translation system "significantly increased international trade on this platform, increasing exports by 17.5%". The effects are "consistent with a substantial reduction in translation-related search costs". [research] (https://www.nber.org/papers/w24917, abstract read; venue and pages checked in Crossref, DOI 10.1287/mnsc.2019.3388, read 2026-10-14) **Transfer:** it is evidence that language is a real search-and-conversion barrier across stores. It is eBay, cross-border export, and a platform-wide system launch. It says nothing about a single Amazon seller's machine-translated listing against a human translation. It does not license a predicted effect size for a translation change.
- **Barrafrem, K., Tinghög, G., "The Effect of The Omnibus Pricing Directive on Consumer Purchase Intentions", Journal of Consumer Policy 49, 2025 (published 2025-12-26).** This was a pre-registered online experiment with 500 UK consumers, where the Directive is not implemented. Displaying the lower 30-day prior price, the "Omnibus Price", "significantly reduced purchase intentions, with a larger effect for utilitarian than for hedonic products". [research] (abstract via Crossref and OpenAlex, DOI 10.1007/s10603-025-09607-z; the Springer page redirected to a sign-in, read 2026-10-14) **Transfer:** this is stated intention, not purchases, in hypothetical scenarios. It still suggests that the same discount converts less in an EU store showing the 30-day low than in the US. That is a reason to judge EU discount effects on their own store series.
- No published study found on Amazon BIL, on GPSR's effect on conversion, or on per-store language tags.

## Stable enough for a skill

- Every Amazon store has its own marketplace id, and every SP-API call goes to the regional endpoint that serves that store (NA, EU or FE). (Marketplace IDs; SP-API Endpoints)
- Catalog data for one ASIN differs by store, and most text attributes are localized per store or locale. (Listings APIs FAQ)
- Image attributes written through the Listings Items API apply to the ASIN in every store where it exists, even when the write names one `marketplace_id`. (Listings APIs FAQ)
- Text attribute values carry `language_tag` and `marketplace_id`. The allowed language tags and lengths for a store live in that store's product type schema. (Submit modular titles; definitionsProductTypes model)
- The seller Sales and Traffic report covers one marketplace per report. (sellerSalesAndTrafficReport schema)
- BIL creates and updates offers and prices from one source store to target stores. A sale price in the source starts a sale in the targets. Exchange-rate adjustments run periodically. A manual change in a target store breaks that offer's connection. (Build International Listings; BIL price rules; Exclude offers)
- BIL attempts to translate and create detail pages that do not exist in a target store and guarantees neither creation nor legal compliance. (Build International Listings)
- Amazon's help pages exist in per-store layers that can differ in substance. The page for the store being changed is the one that applies. (Product title requirements and guidelines, layers US/JP/AE; Use search terms effectively, layers US/GB/DE/JP)
- In Japan, title and Item highlights limits are counted in characters, not bytes. Search-term limits are counted in bytes. (Product title requirements, JP; Use search terms effectively, JP)
- In EU stores, most non-food products need manufacturer, EU Responsible Person and warning or safety information on the detail page, in the store's official language. Amazon deactivates non-compliant listings. (General Product Safety Regulation (GPSR); Submitting manufacturer, Responsible Person, and warning and safety information)
- GPSR safety images go in Amazon's dedicated PS image variants, not the gallery; the variant names are read from the store's layer of the Submitting manufacturer page. (Submitting manufacturer…)
- For CE-marked products sold in the EU, a Responsible Person established in the EU is required. In Great Britain the CE and UKCA marks are both accepted. (Market Surveillance Regulation; EU and UK product marking guidance)
- In EU stores, price-discount thresholds are measured against the store's lowest recent price over the reference period that store's Price discounts page names, not against a Was Price. Amazon.fr displays that prior price on price-reduction announcements. The thresholds themselves change by event and are read from the store's page, never carried in a skill. (Price discounts, DE layer; Reference Pricing and Savings, amazon.fr)
- On amazon.de, the statutory right of withdrawal applies in addition to any longer voluntary return window, whose length is read from the store's returns page. (About Our Returns Policies, amazon.de)

## What cx must read at run time

- **Which stores the seller sells in.** `GET /sellers/v1/marketplaceParticipations` (Sellers API, `getMarketplaceParticipations`). door.md owns the path. The Sellers model confirms that neither Sellers operation (`getMarketplaceParticipations`, `getAccount`) returns a seller id: the reply carries `marketplace` (`id`, `name`, `countryCode`, `defaultCurrencyCode`, `defaultLanguageCode`, `domainName`), `participation` (`isParticipating`, `hasSuspendedListings`) and `storeName`. `defaultLanguageCode` is described as "The ISO 639-1 format language code of the marketplace" while the model's own example value is `en_US`; it names the store's default language, not the set of `language_tag` values the store accepts, which only the schema gives. [official] (sellers.json, https://github.com/amzn/selling-partner-api-models/blob/main/models/sellers-api-model/sellers.json, read 2026-10-14)
- **Which origin to call.** The SP-API endpoint for the store (A1). door.md's table maps origin to refresh token (na / eu / fe).
- **The store's schema.** `getDefinitionsProductType` with one `marketplaceIds`, `requirements=LISTING` and `locale`; `sellerId` is optional ("When provided, seller-specific requirements and values are populated within the product type definition schema, such as brand names associated with the selling partner"), and where cx gets the seller's own id is owned by door.md, not settled here. Read `$defs.language_tag` (enum and default), `$defs.marketplace_id`, and per attribute the `maxLength` / `maxUtf8ByteLength` / `selectors`. Also check whether `title_differentiation`, `gpsr_safety_attestation`, `dsa_responsible_party_address`, `gpsr_manufacturer_reference` and `compliance_media` exist.
- **Before any write, a preview in the target store.** `patchListingsItem` / `putListingsItem` with `mode=VALIDATION_PREVIEW` and that store's `marketplaceIds`. Read `issues`.
- **The listing's state per store.** `getListingsItem` with `marketplaceIds=<the store>`, `includedData=summaries,attributes,issues` and `issueLocale`. Read `issues[].enforcements` for GPSR and compliance deactivations.
- **What shoppers in that store see.** `getCatalogItem` / `searchCatalogItems` (Catalog Items v2022-04-01) with that store's `marketplaceIds`. Data differs by store (A2).
- **Effect series.** Use the Sales and Traffic report or the Data Kiosk seller analytics datasets for one store at a time; door.md owns the report names, options and waits (`createReport`, `getReport`, `getReportDocument`). Brand Analytics reports are likewise per marketplace (door.md).
- **BIL state.** No SP-API operation for BIL was found on any page read. cx asks the seller whether a BIL connection exists, which store is the source, and whether the SKU is excluded. The seller can download the BIL Status report from Seller Central (C5).
- **Keepa.** Keepa's `domain` follows the store (the Keepa skill's references list `1` us, `2` uk, `3` de, `4` fr, `5` jp, `6` ca, `8` it, `9` es, `10` in, `11` mx, `12` br). Competitor series for any other store cannot come from Keepa here.

## Positions

1. **P-marketplaces-and-languages-1.** Every logged change, every read and every effect series names exactly one `marketplace_id`. cx never compares or sums a change's effect across stores in one series. Sources: Marketplace IDs; sellerSalesAndTrafficReport.json; Listings APIs FAQ.
2. **P-marketplaces-and-languages-2.** cx sends each store's calls to that store's regional endpoint (NA, EU or FE) and reads the seller's stores from `marketplaceParticipations` before naming a store. Sources: SP-API Endpoints; Marketplace IDs.
3. **P-marketplaces-and-languages-3.** An image change is logged as affecting every store where the ASIN exists, and effect-review in those other stores lists it as a confounder. Source: Listings APIs FAQ.
4. **P-marketplaces-and-languages-4.** Before proposing a price, sale or offer change in any store, cx asks the seller whether a Build International Listings connection includes that store. If it is a source store, cx lists the target stores the change will reach. If it is a target store, cx tells the seller that a manual change breaks that offer's connection. Sources: Build International Listings; Build International Listings price rules; Exclude offers or products from a target marketplace.
5. **P-marketplaces-and-languages-5.** effect-review in a BIL target store treats price moves without a seller action, such as exchange-rate adjustments or a source-store sale, as confounders. It never reads them as the seller's change. Sources: Build International Listings; Build International Listings price rules.
6. **P-marketplaces-and-languages-6.** cx tells the seller that Amazon does not say whether a hand-edited title or bullet in a target store will survive later BIL syncs or Amazon translation. cx reads that store's listing again after any source-store change. Sources: Build International Listings; Global Offer Manager; Easily Translate Your Product Listings to Sell Globally (staff post).
7. **P-marketplaces-and-languages-7.** Text values are written with `language_tag` and `marketplace_id` in Amazon's snake_case, underscore form, such as `en_US`. The tag is taken from the target store's schema `$defs.language_tag`, never assumed. Sources: Submit modular titles; definitionsProductTypes_2020-09-01.json.
8. **P-marketplaces-and-languages-8.** A change proven in one store is never copied to another store without that store's schema, a `VALIDATION_PREVIEW` and that store's `issues`, because data requirements and help-page rules differ by store. Sources: Listings APIs FAQ; Product title requirements and guidelines (store layers); Use search terms effectively (store layers).
9. **P-marketplaces-and-languages-9.** cx reads the help-page rule for the store being changed. Where Amazon's store layers disagree, as on the title limit in SA, EG, TR and AE and the search-term bytes in JP, cx follows the store's schema and says the pages disagree. Sources: Product title requirements and guidelines (US, AE, SA, EG, TR layers); Use search terms effectively (JP); Keyword attributes explained (JP).
10. **P-marketplaces-and-languages-10.** For Japanese text, cx counts title and Item highlights length in characters and search terms in UTF-8 bytes. Sources: Product title requirements and guidelines (JP layer); Use search terms effectively (JP layer).
11. **P-marketplaces-and-languages-11.** A review of a listing in an EU store checks GPSR content: manufacturer contact, EU Responsible Person, and warning and safety information (or a safety attestation) in the store's official language. A missing item counts as a deactivation risk ahead of any copy change. Sources: General Product Safety Regulation (GPSR); Submitting manufacturer, Responsible Person, and warning and safety information; Update: Support for GPSR compliance in Listings Items API.
12. **P-marketplaces-and-languages-12.** GPSR safety images are proposed only in Amazon's dedicated PS safety-image variants, as named on the store's layer of the Submitting manufacturer page, and in the store's official language. They are never proposed as gallery images. Source: Submitting manufacturer, Responsible Person, and warning and safety information.
13. **P-marketplaces-and-languages-13.** cx does not tell a seller that UKCA is required for Great Britain. Amazon's marking guidance says both CE and UKCA are accepted there, and that EU and Northern Ireland sales need CE plus an EU Responsible Person. Sources: EU and UK product marking guidance: CE and UKCA marking; Market Surveillance Regulation.
14. **P-marketplaces-and-languages-14.** For a discount in an EU store, cx measures the discount and its effect against that store's lowest recent price over the reference period the store's Price discounts page names, not against a US-style Was Price. That low, with the period read, is part of the change log entry; the minimum-discount thresholds are read from the store's page at run time. Sources: Price discounts (DE layer); Reference Pricing and Savings (amazon.fr, amazon.co.uk); Amazon policy on reference prices (DE layer).
15. **P-marketplaces-and-languages-15.** effect-review in EU stores counts returns over a window that covers at least the statutory withdrawal period after delivery, and the store's own longer return window where its returns page states one. The return-data delay recorded in angles/returns.md (ship-date attribution in Data Kiosk) comes on top of that window. Sources: About Our Returns Policies (amazon.de); Manage returns (DE layer); angles/returns.md.
16. **P-marketplaces-and-languages-16.** In Amazon.com.be, cx treats Dutch and English text as Amazon's translation of the French listing unless the seller says they supplied it. Source: Selling on Amazon.com.be, Getting Started Guide (2023).
