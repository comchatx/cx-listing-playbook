# Research for cx-listing-playbook

This directory is the research base for the pi package cx-listing-playbook: the skills listing-review (which carries references/writing.md), listing-change-log and effect-review, the script scripts/report.sh, and two templates, /listing-review and /listing-watch (which writes the standing instruction); every file here was read on 2026-10-14. Sources are weighed in this order and tagged by type: Amazon's own words first, tagged [official] (Seller Central help, SP-API docs and models, Amazon Ads, aboutamazon.com, sell.amazon.com, Amazon staff posts in Seller Forums; Keepa's own documentation and code, and regulators' pages, carry the same tag); then named practitioners and vendors, tagged [opinion]; then published research and Amazon Science, tagged [research]; the researching seat's own reasoning is tagged [seat], and no skill states a [seat] item as fact. Two limits were kept: no Amazon or Keepa API host was called (no `sellingpartnerapi-*`, no `api.keepa.com`; documentation pages only), and no seller data is held here (no store names, seller ids, real seller ASINs or store figures; `<ASIN>` and `<SKU>` stand in). Seller Central help pages were read through the help hub's own content call, as recorded in method/help-page-access.md, and the standing use of that call is for the office to rule.

## How to read this

- Start with the positions below: they are what the skills will say and do, numbered L, W, C, E, S and T so Jack can answer by number.
- Each position names the file and P-id that carries its sources; `P-<file>-N` is in that file's *Positions* section, and the pages behind it are in the same file's *Pages read* table.
- Figures are for human readers and are stated by no skill: they sit under *Facts for human readers only*, and a skill reads the schema, the page or the seller's console at run time instead.

## Positions the skills will take

Each position is one sentence, followed by the P-ids that carry it and the names of its source pages, Amazon's first. ### listing-review

#### The funnel

- **L1.** A review first names the stage that fell (findable, exposure, click-through, conversion, or the offer) and the file and field that show it. — P-funnel-and-search-1, 2; P-triggers-1. [official] Search Catalog Performance schema; Sales and Traffic schema; My ASIN is unsearchable.
- **L2.** Before any wording change, cx checks the gates (parent ASIN, browse node, buyable offer, launch date, search suppression, `issues` with BUYABLE and DISCOVERABLE, the Featured Offer holder, own stock) and reports a gate failure first, because copy fixes none of them. — P-funnel-and-search-3; P-triggers-2; P-search-terms-13; P-price-position-1; P-inventory-and-fulfillment-1, 3. [official] My ASIN is unsearchable; Suppressed listings; Manage Listings Issues; Becoming the Featured Offer; Understanding Amazon listing status and seller-fulfilled inventory management; getInventorySummaries.
- **L3.** Before blaming copy, cx reports any non-copy cause Amazon names: stranded FBA units, inactive or split children, an approval requirement, a pricing-error deactivation, main-image suppression, an adult classification, or an Account Health listing-policy violation. — P-listing-content-and-health-22, 23, 24; P-funnel-and-search-23, 24; P-images-and-video-2. [official] Fix stranded inventory; Pricing Health; Image suppression; Account health rating.
- **L4.** The account layer is read before the listing (participation and suspended listings from `getMarketplaceParticipations`, the seller-performance report and the Account Health rating), and an account cause is named before any content edit is proposed. — P-account-health-1; P-sp-api-access-14; P-triggers-23; P-listing-content-and-health-29. [official] Account health rating; Performance Reports; accountHealthReport-2020-11-18.json; sellers.json; Review Account Health updates for FBM offers.
- **L5.** Every account-health threshold, status and score is taken from what Amazon returns (`targetValue`, `targetCondition`, `status`, the rating fields), never quoted from memory. — P-account-health-3. [official] Performance Reports; accountHealthReport-2020-11-18.json; Account health rating.
- **L6.** An empty `issues` array is not proof that a listing is fine, because Amazon says not every problem has a defined issue and policy removals show elsewhere. — P-account-health-2; P-listing-content-and-health-3. [official] Notification Type Values; Appeal an account deactivation or listing removal; Listings APIs FAQ.
- **L7.** A policy item that names the detail page itself (a trademark on the page, a prohibited claim, a page that does not match the product) may get a content fix, while one about the product, its packaging, authenticity, safety or documents is told plainly as something no listing edit resolves. — P-account-health-5, 6. [official] Intellectual Property Policy; Additional information … Restricted Products policy; Invoice requirements for appealing a policy violation; Safety, compliance, and product restrictions.
- **L8.** cx never advises closing, deleting or zeroing stock on a listing as a fix for an account-health violation. — P-account-health-7. [official] Account health rating; Additional information … Restricted Products policy.

[official] Appeal an account deactivation or listing removal; Account health FAQ; Account Health Assurance FAQ.
- **L10.** An appeal drafted for the seller follows Amazon's structure (the violation and product, the cause, the reactive steps, the proactive steps), and cx never says Account Health Assurance protects a listing, because Amazon says it covers the account. — P-account-health-13, 14. [official] Additional information … Restricted Products policy; Complete an appeal questionnaire to reinstate selling privileges; Account Health Assurance FAQ; Seller Challenge FAQ.
- **L11.** Exposure rests on the title, search terms, item type keyword, browse node and attributes, and Amazon says bullets and description are not always indexed, so they count for search only conditionally. — P-funnel-and-search-4, 5; P-attributes-and-browse-nodes-20, 21; P-description-11, 20. #### Trigger families

- **L26.** A trigger names its family (competitor, demand, own-listing, constraint), the stage it threatens and the file that shows it, and never by itself justifies an edit. — P-triggers-1. [official] Manage Listings Issues. [opinion] Google SRE ch. 6.
- **L27.** A fall in SQP search volume or totals is demand, and a fall in the ASIN's share while totals hold is competition or the listing. — P-triggers-3; P-search-query-performance-1, 6; P-competitor-discovery-3; P-seasonality-and-events-10. [official] SQP schema; Analytics Reports. [research] Seasonal relevance in e-commerce search (Yang et al. 2021). [opinion] Intentwise; ZonGuru.
- **L28.** Constraint triggers are named and handled before any content review: a new seller holding the Featured Offer, a lost Featured Offer, PRICING_HEALTH, an ASIN redirect or merge read from Catalog or Keepa, a change of rank category, a fee-tier change, stranded units with a removal deadline, and a stock or capacity risk. — P-triggers-17, 19, 24, 25, 26, 27, 28; P-inventory-and-fulfillment-6, 7, 20. [official] Becoming the Featured Offer; Pricing Health; Notification Type Values; Fix stranded inventory; Stranded inventory required removals; Fulfillment by Amazon (FBA) Reports; FBA capacity limits; Keepa Product.java.
- **L29.** Returns and Voice of the Customer are own-listing triggers, a listing cause is named only when comments, Listing Insight or review topics agree, and a page-misdescription complaint gets an observation window in weeks. — P-returns-1, 15; P-account-health-10; P-seller-central-only-tools-10; P-funnel-and-search-28. [official] Voice of the Customer; Resolve your CX Health issues; Frequently returned item badge.

[official] Search term reports [v3]; Sponsored ads reporting FAQ (version 3). [opinion] Perpetua; Scale Insights.
- **L31.** A session change without a matching SQP change is read as traffic from outside search, and off-listing activity (Store changes, Sponsored Brands or display, Live, tailored promotions, claim codes) is asked about before a listing gets credit or blame. — P-off-listing-traffic-1, 2. [official] Search Query Performance dashboard; sellerSalesAndTrafficReport.json; Business reports glossary.
- **L32.** Competitor moves (price, promotions, stock, new sellers, content) are read from cx's kept copies and reported as findings for the seller to classify. — P-offer-competition-and-hijackers-1; P-brand-protection-and-catalog-contribution-8; P-triggers-5, 22; P-competitor-set-11. #### Verdicts

- **E40.** There are three verdicts: held (after the control is taken out, the metric moved the expected way by at least the logged smallest move, orders did not fall, nothing else explains it), not held (the window could have seen that move and did not, or it moved the wrong way), and cannot tell (everything else). — P-effect-measurement-18. [research] Controlled experiments on the web; Seven Rules of Thumb.
- **E41.** Every verdict names the exact field it read, uses the same field from the same file in both windows, and states the counts behind it. — P-effect-measurement-17, 24, 44. [official] analytics_sellerAnalytics_2025_03_31.graphql. [research] Seven Rules of Thumb; NIST Poisson Distribution.
- **E42.** Noise is not computed as if each session were an independent shopper: binomial and Poisson intervals are floors, and an overdispersed count model fitted to the ASIN's history sets the noise where history allows. — P-effect-measurement-29; P-triggers-30. [research] NIST/SEMATECH e-Handbook. [opinion] Minitab.
- **E43.** One primary metric is fixed in advance, and a single "significant" query or segment among many is reported as chance unless it survives false-discovery-rate control or a pooled estimate. — P-effect-measurement-31. [research] Benjamini and Hochberg 1995.
- **E44.** Every change has two guardrails, the ASIN's whole-catalog search funnel and its previous top queries the change did not bet on, and a material fall in either blocks "held". — P-effect-measurement-30. [official] Search Catalog Performance schema; analytics_sellerAnalytics_2025_03_31.graphql.
- **E45.** Before the first verdict on an ASIN, a placebo check runs the same rule on past windows with no change, and if it often returns held or not held, verdicts there are cannot tell and MYE is proposed. — P-effect-measurement-32. [research] placebo and synthetic-control sources in effect-measurement.md.
- **E46.** A large win from a small wording change is checked for a data or confounder explanation first, and a listing picked because it dropped is told that some recovery was expected anyway. — P-effect-measurement-16, 19. [research] Seven Rules of Thumb; Regression to the mean.
- **E47.** The expected lifts of several changes are never added into one forecast. — P-effect-measurement-22. [research] Seven Rules of Thumb.
- **E48.** Every held or not held is provisional and re-read at a logged durability window, and a changed reading is added as a dated note that never overwrites the first. — P-effect-measurement-35. [research] Focusing on the Long-term; The preregistration revolution.
- **E49.** A revert is a new change with its own baseline, window and verdict. — P-effect-measurement-36. [research] Design and Analysis of Switchback Experiments.

- **E52.** Returns are a guardrail read only for days older than the return lag Amazon's dataset guide states, and a sooner verdict says returns are not yet in, with returns read alongside conversion for a gallery change. — P-effect-measurement-43; P-returns-21; P-images-and-video-28. ## The seat's own (not for a skill)

These are [seat] reasoning and run lessons. They guide design; no skill states them as fact.

- **Healthy-listing test.** "Catalog equals submitted" fails for many listings once Amazon's title rewrites and other contributors are counted, which is why L57 asks for an explainable difference; on hybrid ASINs the test should name whose value is displayed.
- **Required orders per window.** Poisson arithmetic says a small relative move in orders needs many orders per window, and overdispersion raises that, so most single-ASIN before/after windows cannot see a small change; cannot tell will be common and MYE is preferred.
- **Competitor-control bias.** Competitors lose what the seller wins, so subtracting their fall overstates the effect, while a rival that reacts hides it; a contaminated control withholds "held" rather than correcting by a guess.
- **Stock-outs and the control set.** Competitors' ranks improve while the seller is out of stock, so the set can look like it "rose" during the seller's own outage.
- **Accepted, not displayed.** The ACCEPTED-but-not-shown case should be its own outcome in the change log, distinct from rejected and displayed, with escalation as its next step.
- **Hidden offer causes.** The most common hidden cause of a "failed" change on a brand's own ASIN is an offer event (a stock-out, a lower-priced new seller), so the offer read belongs in the baseline file.
- **FBM offer deactivation.** Of the account-layer causes, the FBM offer-level deactivation is the most likely to be misread as a content problem: the account stays green while one listing goes dark.
- **Hybrid brands.** A hybrid brand is best reviewed per ASIN (which account sells it, which contributed each attribute), its cleanest effect reviews are on single-channel ASINs, and content is best submitted from one account per ASIN.
- **Thin stock is a choice.** The fees push in opposite directions, so a seller running thin is often choosing it, and cx's tone should reflect that.
- **Peak-fee boundary.** A window straddling the start of peak fees also holds Black Friday Week preparations and the start of holiday demand, so a content verdict across it is unlikely to be clean.
- **Report waits.** SQP reports appear to be processed one at a time and can take from minutes to hours, so SQP is a background job collected on a later turn; a `reportDocumentId` already seen on another receipt is the sign of a cached copy; an unexplained "A client error occurred" `FATAL` may be Amazon's own fault.
- **Report quotas.** Report-type limits appear to be metered per seller account and shared with the seller's other applications, so a 429 or `FATAL` may be caused by another tool.
- **False-alarm worked example.** Many watched series at a long average run length still give a steady trickle of false alarms, which is why T3 budgets alarms across the whole watch.
- **Chart design for /listing-watch.** EWMA or CUSUM on each ASIN's own history, with overdispersion-adjusted limits; hard constraints (suppression, a lost Featured Offer, a stock-out) alert on occurrence, not on statistics.
- **Reading order and handoff tree.** A reading follows the funnel (gates, then the stage that fell, then elements), and Seller Central handoffs go in a tree by tool, marketplace and capture date, with metadata beside each file.
- **Competitor tiers.** A small confirmed control set and a wider watch list read daily.
- **Origin-claim check.** A machine check can flag US-origin wording in copy or images against the country-of-origin attribute.
- **Content for the assistant.** Copy written for the assistant should answer the questions shoppers ask (use, audience, compatibility, care, dimensions), following Amazon's own examples.
- **Keepa coverage.** Several stores have no Keepa domain, so effect reviews there may have to answer cannot tell for the competitor subtraction.
- **Retail seller id.** Amazon retail's seller id is widely reported to equal the marketplace id; no Amazon page read says so, and Keepa's `isAmazon` is the documented test.
- **Run lessons (2026-10-13/14, no seller data).** An earlier run showed the sandbox origin as if it were the live store, wrote without reading the schema, used non-schema attribute names and a hyphenated language tag, put an `<ASIN>` where `<SKU>` belongs, and offered a DELETE as a cheap fix, and fell into deleting inactive SKUs without reading why; W1, W5, W10, L58, C20 answer these.
