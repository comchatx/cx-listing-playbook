# Report and query lifecycle: Reports API 2021-06-30 and Data Kiosk 2023-11-15

Read 2026-10-14 by the research seat. Tags: [official] Amazon's own page or document; [opinion] a named practitioner; [research] published research; [seat] the seat's own reasoning, never a skill position.

## What this covers

**Stage:** none of its own. This is plumbing. Every figure that the exposure, click-through and conversion stages are judged on reaches cx through an asynchronous request: a Reports API report (`createReport` → `getReport` → `getReportDocument`) or a Data Kiosk query (`createQuery` → `getQuery` → `getDocument`). This file owns that lifecycle. Most other research files in this package hand "names, options and waits" to door.md (the SP-API door reference, being extended by the sp-api-connect batch), and door.md on main (read 2026-10-14) carries no report-type entries: its report lines are the 5-minute document URL lifetime and "the door adds no wait and retries nothing of its own". [seat, from the tree] The script that runs the lifecycle is `scripts/report.sh` in `listing-review` (create, poll, download, land beside a receipt; read a landed report of the same ask instead of creating again; one wait whose ceiling is an argument; no limiter, no retry of its own); report names, options and waits reach it as the caller's arguments.

**Skills it feeds:**
- `effect-review`: before/after windows are only as good as the report that filled them. If a `CANCELLED` report is read as a failure, a `FATAL` error document is read as data, or only the first Data Kiosk page is read, the verdict is corrupted before any statistics start.
- `listing-review`: the funnel figures (Sales and Traffic, Search Query Performance, Search Catalog Performance, the listings reports) are all reports.
- `listing-change-log`: the observation window has to be written in the periods Amazon will actually accept: one Brand Analytics period per request, Sunday-to-Saturday weeks, and dates that Amazon rolls back.
- **The report script** (create, poll, download): this file is its specification source.
- `/listing-watch`: a standing instruction that triggers on a report must not create duplicates or schedules that collide with the seller's other tools.

**Why a senior operator cares.** On 2026-10-13 cx guessed report names and options and spent its `createReport` budget on them: 25 `createReport` calls in under 15 minutes to deliver the reports it meant, of which 12 answered 400 for names that do not exist, 3 created reports only to learn that a name was valid, 4 ended `FATAL` on options or dates, and 1 was refused 429. It read a report under an ID it had typed itself rather than one Amazon gave it, fetched every document with `curl` into `/tmp` with no receipt, and printed a presigned link into the chat. On 2026-10-14 it chained a second polling loop without telling the seller, then told the seller a report created 17 minutes earlier had been queued "over 24 hours" and offered to create it again (internal run reports, day 1 items 2–5 and day 2 rows B and F). Each of these is a lifecycle error, not an analysis error. An operator also knows something the documentation states only in part: some report types are metered per seller account, across every application and Seller Central itself (Amazon states it for one FBA report, §G). So a seller's other tools can throttle cx, and cx can throttle them.

### A. The Reports sequence (RULE: the API contract)

The operations: `createReport` (`POST /reports/2021-06-30/reports`), `getReports` (`GET /reports/2021-06-30/reports`), `getReport` (`GET …/reports/{reportId}`), `cancelReport` (`DELETE …/reports/{reportId}`), `getReportDocument` (`GET /reports/2021-06-30/documents/{reportDocumentId}`), and four schedule operations under `/reports/2021-06-30/schedules` (`getReportSchedules`, `createReportSchedule`, `getReportSchedule`, `cancelReportSchedule`). [official] (reports_2021-06-30.json `paths`)

1. `createReport` (`POST /reports/2021-06-30/reports`) takes `reportType` and `marketplaceIds` (both required; `marketplaceIds` 1 to 25 entries), plus optional `reportOptions`, `dataStartTime` and `dataEndTime`. `reportOptions` is "Additional information passed to reports. This varies by report type", a map of string to string. It answers HTTP 202 with a `reportId` only. That ID "is unique only in combination with a seller ID"; the model says the same of `ReportDocument.reportDocumentId` and of `reportScheduleId`. [official] (reports_2021-06-30.json, `CreateReportSpecification`, `CreateReportResponse`, responses `202`, https://github.com/amzn/selling-partner-api-models/blob/main/models/reports-api-model/reports_2021-06-30.json, read 2026-10-14; Request a report, https://developer-docs.amazon/sp-api/docs/request-a-report, read 2026-10-14)
2. `getReport` (`GET /reports/2021-06-30/reports/{reportId}`) is polled "until the processingStatus value in the response indicates that processing has ended. Processing will have ended when the processingStatus equals CANCELLED, DONE or FATAL. At this point the response includes a reportDocumentId value if there is report data available." [official] (Verify that report processing is complete, https://developer-docs.amazon/sp-api/docs/verify-that-report-processing-is-complete, page updated 2026-09-09, read 2026-10-14). **No page read gives a polling interval**: "Periodically" is Amazon's only word on it. Polling too early is named as one cause of a 404: "Early polling for a resource that the system hasn't finished generating (for example, a report, processing feed result, or a new listings item)." [official] (Resolve Common HTTP and Authorization Error Codes, https://developer-docs.amazon/sp-api/docs/resolve-common-http-and-authorization-error-codes, "Common 404 error messages", read 2026-10-14)
3. `getReportDocument` (`GET /reports/2021-06-30/documents/{reportDocumentId}`) returns `reportDocumentId`, `url` and, optionally, `compressionAlgorithm`. The steps: "Save the `url`, and `compressionAlgorithm` (optional property)", then download from `url`; Amazon's sample decompresses when `compressionAlgorithm` is `"GZIP"` and takes the charset from the download's `Content-Type` header. [official] (Retrieve a report, https://developer-docs.amazon/sp-api/docs/retrieve-a-report, page updated 2026-09-09, read 2026-10-14)
4. "The getReport operation only serves information for on-demand or scheduled report requests that were created within the last 90 days." [official] (Verify that report processing is complete, same URL)
5. Documentation inconsistency: the tutorial's `getReport` response example wraps the record in `"payload"`. The model's 200 response is the `Report` object itself, with no wrapper. [official] (Verify that report processing is complete; reports_2021-06-30.json `getReport` responses `200`). cx should read the reply as it arrives and not assume the wrapper. [seat]

### B. `processingStatus`: the full enum and what each value means (RULE)

The model's enum is `CANCELLED`, `DONE`, `FATAL`, `IN_PROGRESS`, `IN_QUEUE`, defined as follows [official] (reports_2021-06-30.json, `Report.processingStatus`, x-docgen-enum-table-extension):
- `IN_QUEUE`: "The report has not yet started processing. It may be waiting for another `IN_PROGRESS` report."
- `IN_PROGRESS`: "The report is being processed."
- `DONE`: "The report has completed processing." The tutorial adds: "and a reportDocumentId is available." (Verify that report processing is complete)
- `CANCELLED`: "The report was cancelled. There are two ways a report can be cancelled: an explicit cancellation request before the report starts processing, or an automatic cancellation if there is no data to return."
- `FATAL`: "The report was aborted due to a fatal error." The tutorial adds: "a reportDocumentId might be present. If present, the report represented by the reportDocumentId can explain why the report processing ended." (Verify that report processing is complete)

The FAQ gives **three** reasons for `CANCELLED`, one more than the model [official] (Reports API FAQ, https://developer-docs.amazon/sp-api/docs/reports-faq, read 2026-10-14, "Why was my report cancelled?"):
- "The report was manually cancelled through the API before processing started."
- "No data can be found for the report."
- "You can request some reports (for example, FBA reports) only once within a specified time period. Any subsequent requests that you make for that report type within that period are cancelled. Check the documentation for each report to verify the request type."

So `CANCELLED` is not by itself "no data": Amazon names an explicit cancel, no data, and a repeat inside a type's once-a-period window, and gives no ranking among them. It is not "zero sales" either. `FATAL` with a `reportDocumentId` means the document is an **error document**, not data. [official] (same pages; the FAQ page updated 2026-09-09). *Lead corrected: the leads read `CANCELLED` as "no data". Amazon's status page gives two causes and the FAQ three; a fourth is type-specific (below).*

**Example only.** In Amazon's `REPORT_PROCESSING_FINISHED` example payloads (merchant and vendor), a `CANCELLED` report carries a `reportDocumentId`. No page read states what such a document holds. [official] (Notification Type Values, https://developer-docs.amazon/sp-api/docs/notification-type-values, page updated 2026-09-30, read 2026-10-14)

Report-type pages give specific `CANCELLED` and `FATAL` triggers:
- Sales and Traffic: "The dataStartTime value provided when requesting this report must not be more than two years before the date of the request. If you fail this condition, the request will be cancelled." [official] (Analytics Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-analytics, read 2026-10-14)
- Vendor analytics reports: "If you request a report for a reporting period that is not yet available, the report will not be generated and processingStatus for the report will be FATAL." It sits under each vendor report's "Data availability" line ("The SLA for weekly reporting periods … is the end of the day Monday, 48 hours after the close of the period. The SLA for non-Saturday daily reporting periods is 72 hours after the close of the period"; the Vendor Inventory Report: "Refreshed data is available 72 hours after the close of the period"). This is stated for vendor report types only. The SQP, SCP and Sales and Traffic sections state no availability lag and no such rule; that seller Brand Analytics reports behave the same way is an analogy, not a statement. [official for vendor types] (Analytics Reports, page updated 2026-10-06). *Lead corrected: a search engine's summary attributed a 72-hour availability to SQP; the page does not.*
- The Search Query Performance report's own schema states the FATAL for dates and stores: `dataStartTime` "must correspond to the first day in the reportPeriod that you specify or else a fatal error returns" (and `dataEndTime` the last day), and `marketplaceIds` "must match the marketplaceId of the selling partner account. This report type supports only one marketplaceId per report. If you specify multiple marketplaces, a fatal error returns and report generation fails." [official] (`schemas/reports/sellingPartnerSearchQueryPerformanceReport.json`, https://github.com/amzn/selling-partner-api-models/blob/main/schemas/reports/sellingPartnerSearchQueryPerformanceReport.json, read 2026-10-14)
- A 400 means "Request has missing or invalid parameters and cannot be parsed". The model's sandbox example answers an unknown report type (`BAD_FEE_DISCOUNTS_REPORT`) with `400` "Invalid input". [official] (reports_2021-06-30.json, `createReport` responses `400`, `x-amzn-api-sandbox`)

**Option errors are reported late, not at request time.** Amazon's own error documents, as returned to cx in internal runs and quoted here as Amazon's words:
- `This report type requires the report option(s): reportPeriod, asin.`
- `reportPeriod parameter contains an invalid value. Valid values are DAY, WEEK, MONTH, QUARTER, YEAR` (day 1). A later run got `... Valid values are MONTH, QUARTER, WEEK`.
- `dataEndTime must be a Saturday when reportPeriod=WEEK`
- `dataStartTime must be a Sunday when reportPeriod=WEEK`
- `"dataStartTime and dataEndTime must span exactly one reporting period."`
- `{"errorDetails":"reportPeriod parameter contains an invalid value. Valid values are MONTH, QUARTER, WEEK"}`

Each came back as a `FATAL` report after `createReport` had answered 202; in the research run the refusals took about 10 to 12 minutes in the queue to arrive. A wrong option therefore costs a `createReport` token **and** a place in the queue. [seat, from Amazon's replies recorded in the internal run reports of 2026-10-13, 2026-10-14 and the 2026-10-14 SP-API research run. The SQP schema's "or else a fatal error returns" states it for that report's dates and stores; no Amazon page states in general that options are validated only at processing time, and an unknown report name is refused at once with 400]

### C. The document: 5-minute URL, GZIP, encoding (RULE)

- `ReportDocument.url`: "A presigned URL for the report document. If `compressionAlgorithm` is not returned, you can download the report directly from this URL. This URL expires after 5 minutes." [official] (reports_2021-06-30.json, `ReportDocument`). The tutorial says "This URL expires after five minutes." [official] (Retrieve a report)
- `compressionAlgorithm` has one value, `GZIP`: "If the report document contents have been compressed, the compression algorithm used is returned in this property and you must decompress the report when you download." [official] (reports_2021-06-30.json)
- New parameter since the 2026-04-01 model commit: `enableContentEncodingUrlHeader` on `getReportDocument`. "When `true`, the Content-Encoding header on the returned URL is set to `gzip` instead of the default `identity` when `compressionAlgorithm` is `GZIP`. This allows automatic decompression by HTTP clients." [official] (reports_2021-06-30.json; model commit 0b5887e "enableContentEncodingUrlHeader added to feeds and reports", 2026-04-01; SP-API Release Notes, https://developer-docs.amazon/sp-api/docs/sp-api-release-notes, read 2026-10-14)
- "Why does the report that I download contain cryptic content and is not human readable? Some reports are compressed when you download them. To correctly process reports, you must decompress them." [official] (Reports API FAQ)
- What the URL is: Amazon's terminology defines an "Amazon S3 presigned URL" as "A URL for an S3 bucket from which you can download an object without AWS security credentials or permissions. … The URL expires after five minutes." So whoever holds the link can fetch the report until it expires. [official] (Terminology, https://developer-docs.amazon/sp-api/docs/terminology, page updated 2026-09-09, read 2026-10-14)
- "You must always maintain encryption at rest. Unencrypted report content must never be stored on disk, even temporarily, because reports can contain sensitive information." [official] (Retrieve a report). The Data Protection Policy requires endpoint controls "on all devices that access, process, or store Information, including storage encryption", and defines "Information" as "any information that is exposed through the Amazon Services API, Amazon Portals, or Amazon's public-facing websites". [official] (Amazon Data Protection Policy, https://sellercentral.amazon.com/solution-provider/policy?policyType=DPP&locale=en-US, read 2026-10-14; the page served its text without a sign-in). Whether the box's `/tmp` and its tenant tree meet this is a policy question for the office (see Open questions).
- Restricted reports: "The `getReportDocument` operation is considered a restricted operation only when a restricted report type is specified", and then needs a restricted-data token whose resource is "a specific path, not a generic path" and one of the roles Direct-to-consumer shipping, Tax remittance or Tax invoicing. None of the reports the listing work reads (Brand Analytics, Sales and Traffic, the listings flat files) is such a type. [official] (Retrieve a report; Get authorization to access restricted report types with PII information, https://developer-docs.amazon/sp-api/docs/get-authorization-to-access-restricted-report-types, read 2026-10-14)
- Listing flat files: "This report includes a UTF-8 Byte Order Mark (BOM) as the first 3 bytes." [official] (Inventory Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-inventory, read 2026-10-14)
- "Amazon periodically adds new fields and field values to reports, and the format and structure of document identifiers may change. Ensure that any report parsers ... can handle these types of updates." [official] (Reports API, https://developer-docs.amazon/sp-api/docs/reports-api, read 2026-10-14)
- Deprecated columns "are retained to maintain the original column order". [official] (Reports API FAQ)

### D. Reusing a report instead of creating one: `getReports` (RULE)

- `getReports` (`GET /reports/2021-06-30/reports`) filters by:
  - `reportTypes` (1–10)
  - `processingStatuses` (any of the five)
  - `marketplaceIds` (1–10; "The reports returned will match at least one of the marketplaces that you specify.")
  - `pageSize` (1–100, default 10)
  - `createdSince` ("The default is 90 days ago. Reports are retained for a maximum of 90 days.")
  - `createdUntil` (default now)
  - `nextToken`

  There is no filter on `reportOptions`, `dataStartTime` or `dataEndTime`. "Either reportTypes or nextToken is required." The next page is fetched by calling "the `getReports` operation and include this token as the only parameter. Specifying `nextToken` with any other parameters will cause the request to fail." [official] (reports_2021-06-30.json, `getReports` parameters and `GetReportsResponse.nextToken`)
- Retention: "The retention of generated reports varies by report type. If an explicit retention is not specified for a report type, then the report will be retained for 90 days. If the generated report is not downloaded within the retention period, you can generate the report again." [official] (Report Type Values, https://developer-docs.amazon/sp-api/docs/report-type-values, page updated 2026-09-10, read 2026-10-14). A type's page can set its own: "Order reports are retained for 30 days. If you don't download the reports before they expire, you can generate them again." [official] (Order Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-order, page updated 2026-10-06, read 2026-10-14)
- The `Report` record carries `reportId`, `reportType`, `marketplaceIds`, `dataStartTime`, `dataEndTime`, `reportScheduleId`, `createdTime`, `processingStatus`, `processingStartTime`, `processingEndTime` and `reportDocumentId`. **It does not carry `reportOptions`.** [official] (reports_2021-06-30.json, `Report`). So a record shows the type, stores and data range, but not which ASINs or which `reportPeriod` an SQP report was asked for, nor which `asinGranularity` a Sales and Traffic report used; for those the only record is the asker's own receipt. In the research run the listings report record's `dataStartTime`/`dataEndTime` echoed the request time, not the age of the (cached) data. [seat, from the model and the internal research run]
- Amazon's guidance on throttling points the same way:
  - "Cache results locally rather than re-requesting the same date ranges." [official] (Analytics Reports, Sales and Traffic note)
  - "Cache frequently used data to reduce the need for repeated API requests." [official] (Optimize Rate Limits for Application Workloads, https://developer-docs.amazon/sp-api/docs/strategies-to-optimize-rate-limits-for-your-application-workloads, read 2026-10-14)
- Merchant listings report types: "Reports are not cached by locale. Requesting the same report within the cache period (between one and six hours depending on the number of entries) may return headers in a different locale than requested." The sentence appears on each of the nine listings flat-file types (`GET_FLAT_FILE_OPEN_LISTINGS_DATA`, `GET_MERCHANT_LISTINGS_ALL_DATA`, `GET_MERCHANT_LISTINGS_DATA`, `GET_MERCHANT_LISTINGS_INACTIVE_DATA`, `GET_MERCHANT_LISTINGS_DATA_BACK_COMPAT`, `GET_MERCHANT_LISTINGS_DATA_LITE`, `GET_MERCHANT_LISTINGS_DATA_LITER`, `GET_MERCHANT_CANCELLED_LISTINGS_DATA`, `GET_MERCHANTS_LISTINGS_FYP_REPORT`). It establishes a cache period; that a request inside it gets the cached document is implied, not stated. [official] (Inventory Reports, page updated 2026-10-06). *Lead corrected: the sentence "If you request a report that you requested recently, Amazon may return the same reportDocumentId" is on no Amazon page read. The reuse is a run finding (the research run's three requests inside about two minutes got one `reportDocumentId`) and a practitioner report (GitHub #1074), not Amazon's words.*
- The FBA generation windows work the same way from the other side: "A near real-time FBA report is generated no more than once every 30 minutes. This means that after a near real-time FBA report is generated following your report request, a 30-minute waiting period must pass before Amazon will generate an updated version of that report." "A daily FBA report is generated no more than once every four hours." And: "These frequencies describe how often Amazon generates updated report content. They do not set how many report requests you can submit. However, some FBA report types also limit the number of requests Amazon accepts." [official] (FBA Reports, https://developer-docs.amazon/sp-api/docs/report-type-values-fba, page updated 2026-10-13, read 2026-10-14). The page does not say what a request inside the window returns (the previous version, or `CANCELLED` as the FAQ's once-a-period rule would have it).

### E. `cancelReport` (RULE)

`DELETE /reports/2021-06-30/reports/{reportId}`: "Only reports with `processingStatus=IN_QUEUE` can be cancelled. Cancelled reports are returned in subsequent calls to the `getReport` and `getReports` operations." [official] (reports_2021-06-30.json, `cancelReport`)

### F. Schedules (RULE)

- `createReportSchedule` (`POST /reports/2021-06-30/schedules`, HTTP 201 on success) takes `reportType`, `marketplaceIds` and `period` (all required), plus optional `reportOptions` and `nextReportCreationTime`. "If a report schedule with the same report type and marketplace IDs already exists, it will be cancelled and replaced with this one." [official] (reports_2021-06-30.json; Schedule and retrieve reports, https://developer-docs.amazon/sp-api/docs/schedule-and-retrieve-reports, read 2026-10-14)
- Allowed `period` values: `PT5M`, `PT15M`, `PT30M`, `PT1H`, `PT2H`, `PT4H`, `PT8H`, `PT12H`, `P1D`, `P2D`, `P3D`, `PT84H`, `P7D`, `P14D`, `P15D`, `P18D`, `P30D`, `P1M`. [official] (reports_2021-06-30.json, `CreateReportScheduleSpecification.period`)
- `getReportSchedules` requires `reportTypes` (1–10). `getReportSchedule` and `cancelReportSchedule` take a `reportScheduleId`. [official] (reports_2021-06-30.json)
- Only some report types can be scheduled. Each type's page says "This report can only be requested" or "can be requested or scheduled":
  - Can be requested or scheduled: `GET_SALES_AND_TRAFFIC_REPORT` and `GET_MERCHANTS_LISTINGS_FYP_REPORT`.
  - Request only: the Brand Analytics SQP, SCP, Search Terms, Market Basket and Repeat Purchase reports, and `GET_MERCHANT_LISTINGS_ALL_DATA`.

  [official] (Analytics Reports; Inventory Reports)
- Scheduled reports are collected through the `REPORT_PROCESSING_FINISHED` notification, delivered by Amazon SQS: "Periodically poll the Amazon Simple Queue Service (Amazon SQS) queue for a REPORT_PROCESSING_FINISHED notification event using an interval that is similar to the schedule". [official] (Schedule and retrieve reports). The notification "is sent whenever any report that you have requested using the Selling Partner API for Reports reaches a report processing status of DONE, CANCELLED, or FATAL". It carries `accountId`, `reportId`, `reportType`, `processingStatus` and, not required, `sellerId` and `reportDocumentId`; its workflow is the "Amazon Simple Queue Service workflow", and it "supports `filterExpression` for CEL-based filtering". [official] (Notification Type Values, https://developer-docs.amazon/sp-api/docs/notification-type-values, read 2026-10-14)

### F2. Polling or notifications (GUIDANCE)

- The tutorials split by route: the on-demand tutorial ("Verify that report processing is complete") polls `getReport`; the schedule tutorial and "Retrieve automatically generated reports" poll the SQS queue for `REPORT_PROCESSING_FINISHED`, "which provides information when the report processing is `CANCELLED`, `DONE` or `FATAL`". [official] (Verify that report processing is complete; Schedule and retrieve reports; Retrieve automatically generated reports, https://developer-docs.amazon/sp-api/docs/retrieve-automatically-generated-reports, read 2026-10-14)
- "Why do some reports take so long to generate? Report generation can take longer depending on the report size, current system load, and the number of processed or queued reports. Use the Notifications API to receive a notification after the report you requested is ready for download." [official] (Reports API FAQ)
- Under "What should I do if my application is consistently throttled?": "Rely on push notifications instead of polling mechanisms." For dynamic usage plans: "Do not hardcode timers." and "Code naturally against events rather than running on a loop." [official] (Usage Plans and Rate Limits, https://developer-docs.amazon/sp-api/docs/usage-plans-and-rate-limits, page updated 2026-09-09, read 2026-10-14). The timer sentences are said of dynamic plans, not of report waits.
- "Smart data retrieval: Structure your system to request data based on when data is likely to be available instead of continuously polling. For report processing, align your polling with report generation schedules." [official] (Optimize Calls to the Selling Partner API, https://developer-docs.amazon/sp-api/docs/optimize-calls-to-the-selling-partner-api, page updated 2026-09-09, read 2026-10-14)
- A notification needs a destination the application owns: an SQS queue or EventBridge. `createDestination` and the other destination operations are grantless; `createSubscription` needs "The role that is associated with the notification type", so the subscription is made with the seller's authorization. [official] (Notifications API, https://developer-docs.amazon/sp-api/docs/notifications-api, read 2026-10-14). Whether ComChatX's application has a destination cx can read is not stated in any of this package's sources. [seat]

### G. Rates: per operation, per report type (RULE, with the numbers living in the model)

Default usage plans as stated in the model and on each operation's reference page (identical on both, read 2026-10-14) [official] (reports_2021-06-30.json; createReport / getReport / getReportDocument / getReports / cancelReport / createReportSchedule reference pages, https://developer-docs.amazon/sp-api/reference/<operation>). Each operation's description adds: "The table above indicates the default rate and burst values for this operation. Selling partners whose business demands require higher throughput may see higher rate and burst values than those shown here."

| Operation | Rate (req/s) | Burst |
|---|---|---|
| `createReport` | 0.0167 | 15 |
| `getReport` | 2 | 15 |
| `getReports` | 0.0222 | 10 |
| `getReportDocument` | 0.0167 | 15 |
| `cancelReport` | 0.0222 | 10 |
| `createReportSchedule`, `getReportSchedules`, `getReportSchedule`, `cancelReportSchedule` | 0.0222 | 10 |

How these limits work, from Amazon's pages:
- Rates are a token bucket ("Each request that you make to the SP-API subtracts a token from the bucket. Throttling occurs when you make a request for which no token is available"), and "Requests are rate limited by whichever threshold you reach first." "Most operations' rate limits are per the selling partner and application pair." [official] (Usage Plans and Rate Limits, https://developer-docs.amazon/sp-api/docs/usage-plans-and-rate-limits, read 2026-10-14)
- "Rate limits for dynamic usage plans auto-adjust higher or lower depending on business context." [official] (Usage Plans and Rate Limits)
- The applied plan is returned in `x-amzn-RateLimit-Limit`: the header "is for HTTP status codes 20x, 400 and 404. Unauthorized, or unauthenticated request, don't include this header", and "you must not depend on this header being present". [official] (Usage Plans and Rate Limits). In the Reports model the header is declared on the 2xx, 400 and 404 replies and not on the 429. [official] (reports_2021-06-30.json, `createReport` responses)
- "A 429 is a retry-able status code. You can try again, but repeated throttled requests require a back-off strategy." [official] (Usage Plans and Rate Limits). "Wait a few minutes, then retry the request." [official] (Resolve Common HTTP and Authorization Error Codes, "HTTP 429 Too Many Requests")

### I. `dataStartTime` / `dataEndTime`: defaults, truncation, periods (RULE)

- Both default to "now", and "The value must be prior to or equal to the current date and time. Not all report types make use of this." [official] (reports_2021-06-30.json `CreateReportSpecification`; Request a report)
- Sales and Traffic expands the range to whole periods: "When dateGranularity is WEEK or MONTH the dataStartTime and dataEndTime values are expanded to that level of granularity. For WEEK the beginning is Sunday and the end is Saturday, and for MONTH the beginning is the first day of the month and the end is the last day of the month." The page continues:
  - "If the expanded dataStartTime value is more than two years before the date of the request, then it will be corrected to be within two years of the request date provided the original dataStartTime is with two years of the request date."
  - "If the expanded dataEndTime value is in the future, then the report will contain partial data for the most recent report period."

  [official] (Analytics Reports)
- Brand Analytics types do **not** expand; they reject. "The dataStartTime and dataEndTime values must correspond to valid first and last days in the specified reportPeriod. For example, dataStartTime must be a Sunday and dataEndTime must be a Saturday when reportPeriod=WEEK." SQP and SCP: "Requests cannot span multiple periods. For example, a request at WEEK level could not start on 2025-01-05 and end on 2025-01-18 as this would span two weeks." [official] (Analytics Reports)
- SQP lists "Maximum reporting periods: The maximum reporting periods that you can specify using the dataStartTime and dataEndTime parameters, by reportPeriod type: DAY: N/A, WEEK: N/A, MONTH: 17 months, QUARTER: N/A, YEAR: N/A". [official] (Analytics Reports). Its wording describes a request span, but the same entry says a request cannot span more than one period, and DAY and YEAR are not valid `reportPeriod` values for SQP. The figure is unexplained on the page (Open questions). It is not a retention or lookback figure on the page's own terms: the page's "Maximum lookback windows" heading ("The maximum lookback windows (from the current date) that are available for each `reportPeriod` type") appears only under the vendor reports, and the SQP entry has none, so the page states no history depth for SQP. [official] (Analytics Reports, page updated 2026-10-06, re-read 2026-10-14). The only Amazon statement of depth read is general to Brand Analytics, from the seller blog's Demographics section: "Data in Brand Analytics usually goes back three years and is generally available within three days, with quarter-end data typically available within one week." [official, a marketing blog, not an API page] (Amazon Brand Analytics: Get data to grow your business, Daisy Quaker, Oct 8, 2025, https://sell.amazon.com/blog/brand-analytics, read 2026-10-14). The Sales and Traffic two-year rule (§B) and the Data Kiosk two-year `startDate` rule are about other reports. How far back a given SQP request reaches is settled by that request's outcome at run time, not by any of these figures.
- Date form: Amazon's Date and Time Formatting page says date-time data "is expressed as Gregorian calendar dates (year, month, day) **and** 24-hour time. No truncated formats are allowed." [official] (Date and Time Formatting, https://developer-docs.amazon/sp-api/docs/iso-8601, read 2026-10-14). The Reports model types both fields `date-time`, while the SQP schema types them `date`. The two Amazon texts conflict on their face for SQP (Open questions; practitioners in GitHub #5065).
- Data Kiosk seller analytics truncates as follows [official] (Seller Analytics Dataset Use Case Guide, https://developer-docs.amazon/sp-api/docs/seller-analytics-dataset-guide, read 2026-10-14, "Date behavior"):
  - Weekly: "The startDate is rolled back to the preceding Sunday and the endDate is rolled back to the preceding Saturday ... After adjustment the range must span at least seven days".
  - Monthly: "The `startDate` is rolled back to the first day of its month. If the `endDate` is not already the last day of a month, it is rolled back to the last day of the preceding month".
  - Availability: "The endDate is additionally capped to the most recent date for which all requested metrics have data."
  - Range: "`startDate` must be in the past, `startDate` must be before or equal to `endDate`, and `startDate` must be no more than two years ago."

### J. Data Kiosk lifecycle (RULE)

1. **Create.** `createQuery` (`POST /dataKiosk/2023-11-15/queries`) takes `query`, a GraphQL string that "must be at most 8000 characters after unnecessary whitespace is removed", and an optional `paginationToken`. It returns `queryId`. [official] (dataKiosk_2023-11-15.json, `CreateQuerySpecification`, https://github.com/amzn/selling-partner-api-models/blob/main/models/data-kiosk-api-model/dataKiosk_2023-11-15.json, read 2026-10-14)
2. **Status.** `getQuery` (`GET /dataKiosk/2023-11-15/queries/{queryId}`) uses the same five-value `processingStatus`. The meanings differ in one place: Data Kiosk's `CANCELLED` is "The query was cancelled before it began processing." Unlike Reports, "no data" is **not** a `CANCELLED`. [official] (dataKiosk_2023-11-15.json, `Query.processingStatus`)
3. **Outcome.** "The response also includes one of the following: A dataDocumentId value if data is available as a result of the query. An errorDocumentId value if there is an error while processing the query. Neither of these when there is no data returned as a result of processing the query." [official] (Verify that query processing is complete, https://developer-docs.amazon/sp-api/docs/verify-query-processing, read 2026-10-14). Also: "A processingStatus of DONE with no errorDocumentId or dataDocumentId in the response of the getQuery operation means that the request completed with no data or that there is no data for the given date range. Retry the request with different parameters." [official] (Data Kiosk API, https://developer-docs.amazon/sp-api/docs/data-kiosk-api, page updated 2026-09-09, read 2026-10-14). The data document is JSONL. The error document is JSON. [official] (Data Kiosk API)
4. **Document.** `getDocument` (`GET /dataKiosk/2023-11-15/documents/{documentId}`) returns `documentUrl`: "A presigned URL ... This URL expires after 5 minutes. If the Data Kiosk document is compressed, the `Content-Encoding` header will indicate the compression algorithm." [official] (dataKiosk_2023-11-15.json, `GetDocumentResponse`). The workflow guide says: "Note that this differs from how the Reports API handles compression. Even if the notification returned an errorDocumentId, you can still use it with the getDocument operation". [official] (Building Data Kiosk workflows guide, https://developer-docs.amazon/sp-api/docs/data-kiosk-workflow-guide, read 2026-10-14)
5. **Pagination.** "When a query produces results that are not included in the data document, pagination occurs. ... To retrieve the next page, you must pass a `CreateQuerySpecification` object with `paginationToken` set to this object's `nextToken` and with `query` set to this object's `query` in the subsequent `createQuery` request. When there are no more pages to fetch, the `nextToken` field will be absent." [official] (dataKiosk_2023-11-15.json, `Query.pagination`; same text in Data Kiosk Query Processing Finished Notification, https://developer-docs.amazon/sp-api/docs/data-kiosk-notification, read 2026-10-14). **Each further page is a new `createQuery`, with its own token from the 0.0167/s bucket, its own queue wait and its own document.** [official, same sources]
6. **Listing queries.** `getQueries` filters by `processingStatuses`, `pageSize` (1–100), `createdSince` (default 90 days ago) and `createdUntil`. Its own pagination uses `paginationToken` from `pagination.nextToken`. "All other parameters must be provided with the same values ... with the exception of `pageSize`". [official] (dataKiosk_2023-11-15.json, `getQueries`)
7. **Cancel.** `cancelQuery` (`DELETE /dataKiosk/2023-11-15/queries/{queryId}`): "Only queries with a non-terminal `processingStatus` (`IN_QUEUE`, `IN_PROGRESS`) can be cancelled. Cancelling a query that already has a `processingStatus` of `CANCELLED` will no-op." Unlike `cancelReport`, it also works on `IN_PROGRESS`. [official] (dataKiosk_2023-11-15.json)
8. **Concurrency.** Amazon says:
   - "The Data Kiosk API does not support query backlogging. Data Kiosk limits the number of concurrent non-terminal queries per selling partner and per GraphQL query."
   - "Data Kiosk only allows one request per query / selling partner / application combination. If there is already a pending request for a given query / selling partner / application combination, the createQuery request will fail."

   [official] (Data Kiosk API). The workflow guide adds: "a 429 error can occur if there's already a query from the same domain in progress ... This could involve either waiting for the in-progress query to complete or canceling it using the cancelQuery endpoint before submitting another", and "Data Kiosk processes queries on a first-come, first-served basis. A newly submitted query will only be processed after the previous query has completed its processing." [official] (Building Data Kiosk workflows guide). **No page read states the number of concurrent queries allowed** (Open questions).
9. **Rates.** The usage plans are the same shape as Reports: `createQuery` 0.0167/15, `getQuery` 2.0/15, `getQueries` 0.0222/10, `getDocument` 0.0167/15, `cancelQuery` 0.0222/10. "Data Kiosk rate limits are the same as the Reports API." [official] (dataKiosk_2023-11-15.json; createQuery / getQuery / getDocument / cancelQuery reference pages; Building Data Kiosk workflows guide)
10. **Retention.** "Each field within a schema is annotated with a `@resultRetention` directive ... the shortest (minimum) retention is applied. The retention of a query's resulting documents always matches the retention of the query." [official] (dataKiosk_2023-11-15.json, `createQuery`). In the three seller-side schemas read, every annotated field carries `@resultRetention(duration: "P30D")`. [official] (analytics_salesAndTraffic_2024_04_24.graphql, analytics_sellerAnalytics_2025_03_31.graphql, analytics_economics_2024_03_15.graphql in amzn/selling-partner-api-models `schemas/data-kiosk/`, read 2026-10-14)
11. **No server-side schedule.** "The Data Kiosk API does not support query scheduling." [official] (Data Kiosk API). The "Schedule Data Kiosk Queries" guide is about a client-side scheduler (EventBridge). It warns: "Query creation fails if the previous query is still running", and "don't create multiple schedules for the same query". [official] (Schedule Data Kiosk Queries, https://developer-docs.amazon/sp-api/docs/schedule-data-kiosk-queries, read 2026-10-14)
12. **Errors come in two kinds.** "Synchronous errors: These errors occur during the initial query creation process ... Typically ... syntax issues in the query". "Asynchronous errors ... are fetched in the form of error documents." [official] (Building Data Kiosk workflows guide). The seller analytics guide lists the asynchronous texts, among them:
    - "The requested metrics are not yet available for <date>. The latest date these metrics are available at the <granularity> granularity is <date>"
    - "Invalid date range for weekly aggregation. The provided date range must span at least 7 days"
    - "Unauthorized marketplace access"

    [official] (Seller Analytics Dataset Use Case Guide)
13. **Visibility and roles.** "Data Kiosk request visibility is limited to requests submitted by a given application". The Data Kiosk API page lists Brand Analytics as the required role ("Required roles (need at least one)") for each of the five operations. **Amazon's pages disagree on the role per dataset:** the changelog note "Correction: Data Kiosk role requirements" says "The initial version of that announcement stated that all datasets require the Brand Analytics role. This is not correct. The Vendor Analytics and Sales and Traffic datasets require the Brand Analytics role. The Economics dataset requires the Selling Partner Insights role." It names no role for the Seller Analytics dataset, and the Economics schema carries no role or PAAM annotation. [official, the two disagree] (Data Kiosk API, page updated 2026-09-09; Correction: Data Kiosk role requirements, https://developer-docs.amazon/sp-api/changelog/correction-data-kiosk-role-requirements, read 2026-10-14; analytics_economics_2024_03_15.graphql). Neither page is preferred here: the binding answer for a given field is Data Kiosk's own per-field check at `createQuery`, read at run time. "Each field available with Data Kiosk requires a certain role. Data Kiosk determines whether the requester has the required roles for each field in the query upon query creation. This authorization paradigm is much more granular than the Reports API. Additionally, queries are only visible to the requester." [official] (Data Kiosk API). Seller analytics fields carry `@paamRights(require: ["analytics_sales_and_traffic_view_pa", ...])`, and "Requesting a field your application is not authorized for returns an authorization error rather than a null value." [official] (analytics_sellerAnalytics_2025_03_31.graphql; Seller Analytics Dataset Use Case Guide)
14. **Readiness and nulls (seller analytics).**
    - "All metrics in the seller analytics dataset are ready after 34 hours. Data for a given day is generally available at 10 AM local time two days later."
    - "In the event that data is delayed and unavailable, the response is null".
    - "This scenario occurs when data is requested within one to two business days. In such cases, the response for periods that are unavailable contains null values."
    - Returns: "Return data is computed with a delay of about 45 days".
    - A null in a grouped row means "this metric is not available at this granularity" rather than zero.

    [official] (Seller Analytics Dataset Use Case Guide)

    - `analytics_salesAndTraffic_2023_11_15`: the release headed August 27, 2025 says "The following dataset will be removed on February 26, 2026"; the SP-API Deprecation Schedule lists the same dataset with removal date March 27, 2026. Either way it is gone by the date of this file.

    [official] (SP-API Release Notes, page updated 2026-10-01; SP-API Deprecation Schedule, https://developer-docs.amazon/sp-api/docs/sp-api-deprecations, read 2026-10-14; Data Kiosk API). ## What practitioners add

- **SQP and SCP are slow, and many ASINs return nothing.** Openbridge Support ("Amazon Search Query Performance & Search Catalog Performance", Openbridge Help Center, dated 2026-03-19):
  - Data is available "about 48 hours after period close".
  - "anywhere from 10-40% of ASINs in a Search Catalog Report will not return a SQP ASIN report".
  - "Each report is a separate request and process to the API".
  - A "practical limit of 100-240 ASIN reports a day".
  - Pull the catalog report first, then SQP only for the ASINs it lists.

  [opinion] Openbridge describes one ASIN per request, while Amazon has accepted a space-separated list since 2025-06-25. A commenter on GitHub #5240 (spiohq, 2026-05-21) notes the 200-character cap allows about 18 ASINs per request. Amazon's staff reply on the same thread agreed with the arithmetic.
- **SQP throughput collapses without notice.** deschoene (GitHub #5240, opened 2026-05-18) reported daily SQP completions of 12 to 26 from 2026-05-07 to 2026-05-18, against about 138 a day in the April cycle, relaying an Amazon Solution Provider Support line: "The current limit of 20 report requests per day is by design and applies to all developers using this report type. This is a system-level quota that cannot be increased on a per-application basis." They also reported that "Calls to `getReport()` on still-queued reports return `null` for `processingStartTime`." jimmy-ross (2026-05-19) saw a single SQP download inside Seller Central take "30 mins - 1 hour"; joshuaba-Spin (2026-05-19) saw a brand-level query in Vendor Central go from "about 3 minutes" to "about 3 hours". deschoene (2026-05-26) said throughput "recovered on our side around 22 May with no change on our end". [opinion; the support quote is hearsay relayed by a developer, and the 20-a-day figure is on no Amazon page]

### Run findings (ComChatX's own beta runs; observations on one United States store, not rules)

From the day-1 report (2026-10-13), the day-2 report (2026-10-14) and the read-only research run of 2026-10-14 05:17 (`office-mailbox/from-engineering/`):
- **Names.** On day 1, 12 `createReport` calls answered 400 for report names that do not exist (one was a documentation placeholder sent as written); 3 more created reports only to learn that a name was valid.
- **Options and dates.** The FATAL texts in §B, each after a 202, each with its reason in the downloaded document.
- **Waits.** A 30-day Sales and Traffic report reached `DONE` in under 2.5 minutes. SQP stayed `IN_QUEUE` for at least 9 minutes on day 1 (stopped by the seat) and at least 17 minutes on day 2. In the research run a new SQP week took 35 min 44 s and 35 min 29 s to process, the same week asked again about 12 minutes, and a refusal 10 to 12 minutes; the store's SQP reports were processed one at a time, each starting when its predecessor ended, consistent with Amazon's "It might be waiting for another IN_PROGRESS report". *Lead corrected: the "~35 minutes" figure is from the research run, not from the two beta runs.*
- **Cache.** The research run sent `GET_MERCHANT_LISTINGS_ALL_DATA` three times within about two and a half minutes (twice back to back, once after the first was `DONE`); all three ended `DONE` with the first's `reportDocumentId`. Across seven hours the store's listings documents were reused for up to about an hour each, inside Amazon's "between one and six hours". The same SQP week asked date-only and date-time got one document.
- **Others' reports.** The research run's `getReports` listed 63 listings reports for the seller's four stores in the region that it had not made, created about hourly.
- **429.** On day 1 one `createReport` was refused 429 under three minutes into a burst of creates; cx waited about 95 s, retried once and got 202.
- **A wrong id.** A report id cx typed itself returned a different, finished report of the store (an order report).
- **Fetching.** Every document was fetched with plain `curl` from the presigned link into `/tmp`, with no receipt; day 1 printed a whole presigned link into the chat.
- **Waiting.** On day 2 cx ran one wait (6 × 45 s), chained a second (8 × 60 s, stopped after 43 s) without telling the seller, made two more unasked status reads, and told the seller a report created 17 minutes earlier had been queued "over 24 hours".

Practitioners disagree with Amazon on one point that matters here. The documentation implies an operation bucket of 15 then 1 a minute for `createReport`, while practitioners report report-type caps that the documentation omits or added later. A skill can only rely on Amazon's reply (`429`, `CANCELLED`, `FATAL` and its error document), never on a figure.

## Published research

- Fabijan, Gupchup, Gupta, Omhover, Qin, Vermeer, Dmitriev, "Diagnosing Sample Ratio Mismatch in Online Controlled Experiments: A Taxonomy and Rules of Thumb for Practitioners", KDD 2019 (authors' version at exp-platform.com, read 2026-10-14). Narrow finding: data-quality failures in log collection and processing ("Experiment Log Processing") are a distinct class of cause behind wrong experiment conclusions, and "Ignoring the SRM without knowing the root cause may result in a bad product modification appearing to be good and getting shipped to users, or vice versa." [research]. **Transfer:** weak and only by analogy. A listing effect review is a before/after comparison, not a randomized experiment, and has no sample ratio to check. The transferable point is that a pipeline which silently loses part of the data looks like an effect. Examples here would be a first Data Kiosk page only, a cached listings copy, or a `CANCELLED` read as zero sales.
- Marc Brooker, "Exponential Backoff And Jitter", AWS Architecture Blog, 2015-03-04 (with an update note of May 2023), linked from Amazon's own "Optimize Rate Limits for Application Workloads". Narrow finding, from simulation: with many clients retrying against a contended resource, adding randomness to the back-off spreads retries and cuts total work; "The 'Full Jitter' approach uses less work, but slightly more time" than "Decorrelated Jitter", and "The return on implementation complexity of using jittered backoff is huge". [research — engineering note, not peer-reviewed] **Transfer:** only to how a caller backs off after a 429. It says nothing about report queues, and the report script does no back-off of its own. (https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/, read 2026-10-14)
- No published research was found on asynchronous report pipelines or polling strategies for marketplace APIs.

## Stable enough for a skill

1. A report is asynchronous: `createReport` returns only an ID, `getReport` is read until the status is `DONE`, `CANCELLED` or `FATAL`, and only then does `getReportDocument` give a download link. (Request a report; Verify that report processing is complete; Retrieve a report)
2. `IN_QUEUE` and `IN_PROGRESS` mean "not finished", not "failed". `IN_QUEUE` can mean waiting behind another report. (reports_2021-06-30.json)
3. `CANCELLED` means this request gives no report to read. Amazon names three causes: an explicit cancel before processing, no data for the request, or a repeat of a once-per-period report. It is not by itself "no data", never "zero sales", and not an error to retry blindly. (Verify that report processing is complete; Reports API FAQ; reports_2021-06-30.json)
4. `FATAL` means the report failed. If a document ID is present, that document can explain the failure and is not data; it is not guaranteed to be present. (Verify that report processing is complete)
5. A 202 from `createReport` does not mean the options or dates were valid; some option and date errors surface as `FATAL` later, while an unknown report name is refused at once with 400. (sellingPartnerSearchQueryPerformanceReport.json "or else a fatal error returns"; reports_2021-06-30.json; internal runs [seat])
6. The download link from `getReportDocument` or `getDocument` expires minutes after it is issued, so it is fetched at once, never stored and never shown. The lifetime is stated in the model. (reports_2021-06-30.json; dataKiosk_2023-11-15.json)
7. A report document may be GZIP-compressed when `compressionAlgorithm` says so. A Data Kiosk document signals compression in its `Content-Encoding` header instead. (reports_2021-06-30.json; Building Data Kiosk workflows guide)
8. Before creating a report, `getReports` with the report type, store and creation window lists the reports already made, with their data range and status, but a report record does not carry the `reportOptions` it was asked with, so only the asker's own receipt can show that a past report matches the same ask. Its next page is fetched with `nextToken` alone. (reports_2021-06-30.json, `getReports`, `Report`)
9. Only `IN_QUEUE` reports can be cancelled. Data Kiosk queries can be cancelled while `IN_QUEUE` or `IN_PROGRESS`. (reports_2021-06-30.json; dataKiosk_2023-11-15.json)
10. A new schedule for the same report type and stores replaces the existing one, whoever made it. Only types whose page says "requested or scheduled" can be scheduled. (reports_2021-06-30.json; Analytics Reports; Inventory Reports)
11. Rates are per operation (most per seller-and-application pair) and, for some types, per report type on that type's page; the printed figures are defaults and can change. The applied plan comes back in `x-amzn-RateLimit-Limit` when present, which is not guaranteed, and a 429 asks for back-off, not a loop. (Usage Plans and Rate Limits; Optimize Rate Limits for Application Workloads; Analytics Reports; FBA Reports)
12. Brand Analytics reports take exactly one period per request, with dates on the period's first and last day: a week runs Sunday to Saturday. Sales and Traffic instead widens the dates to whole periods. (Analytics Reports)
13. A listing flat file is per store (the first `marketplaceId` only), starts with a UTF-8 byte order mark, and has a cache period whose length the Inventory Reports page states (read there at run time, not from a skill), which Amazon mentions only to warn that a repeat request inside it "may return headers in a different locale than requested"; that a repeat may get an older copy is inferred from the sentence and witnessed in an internal run, not stated, and the record does not show the document's age. (Inventory Reports)
14. A Data Kiosk query that finishes `DONE` with neither a data nor an error document had no data for that range. (Data Kiosk API; Verify that query processing is complete)
15. A Data Kiosk result is complete only when the query record carries no `pagination.nextToken`. Each further page is a new `createQuery` with the same `query` and the token. (dataKiosk_2023-11-15.json)
16. Data Kiosk refuses a second identical pending query, and processes queries one after another. (Data Kiosk API; Building Data Kiosk workflows guide)
17. Data Kiosk weekly and monthly ranges are rolled back to whole periods, and the end date is capped at the last date with data. Recent days can be null rather than zero. (Seller Analytics Dataset Use Case Guide)
18. Reports and Data Kiosk results are kept for a limited time stated by Amazon (Report Type Values; Order Reports; `@resultRetention` in each schema), and `getReport` serves only reports created within the window the verify page states. A record of what was read must keep the file, not the ID.
19. A report or document id means something only together with the seller it was made for. (reports_2021-06-30.json)
20. Amazon requires report content to be kept encrypted at rest and never stored unencrypted on disk, even temporarily. (Retrieve a report; Data Protection Policy)
21. "Amazon periodically adds new fields and field values to reports, and the format and structure of document identifiers may change"; a reader keys on column or field names and never parses an id. Deprecated columns stay in place "to maintain the original column order". (Reports API; Reports API FAQ)
22. Amazon prefers the `REPORT_PROCESSING_FINISHED` notification to polling; the notification needs an SQS or EventBridge destination the application owns. (Reports API FAQ; Usage Plans and Rate Limits; Notification Type Values; Notifications API)
23. The Acceptable Use Policy asks an application to respect per-user throttling quotas, minimise client-side errors and retrieve only what its function needs. (Amazon Acceptable Use Policy 2.9, 3.8)
24. Report types are added and deprecated by release note; the live list is the report-type-values pages and the Deprecation Schedule, not a skill. (SP-API Release Notes; SP-API Deprecation Schedule; Reports API FAQ)

## What cx must read at run time

- **Report type names, `reportOptions`, period rules, schedulability, waits and per-type limits:** door.md's (the SP-API door reference owns them; today it has none, so the entries are still to be written). Its sources are the Report Type Values pages (Analytics, Inventory, Performance and the others).
- **Status:** `getReport` (`processingStatus`, `processingStartTime`, `processingEndTime`, `reportDocumentId`). For several reports at once, `getReports` with `reportTypes`, `processingStatuses`, `marketplaceIds` and `createdSince`, then `nextToken` alone for further pages.
- **Reuse:** first the tree (the script's own landed receipt, which holds the body it sent, options included); then `getReports` before `createReport`. The existing record's `reportType`, `marketplaceIds`, `dataStartTime`, `dataEndTime`, `createdTime` and `reportDocumentId` show whether it can cover the window, but not its options, so a record with no matching receipt is a candidate, not a match.
- **Document:** `getReportDocument` (`url`, `compressionAlgorithm`, optional `enableContentEncodingUrlHeader`), fetched through the box's own download, never an echoed link. The URL lifetime is the model's.
- **Error text:** the document behind a `FATAL` report's `reportDocumentId`, or behind a Data Kiosk `errorDocumentId` via `getDocument`.
- **Throttle state:** `x-amzn-RateLimit-Limit` on the reply when present (the defaults in the model's operation description otherwise), and the 429 itself (door.md lands it as `provider_rate_limit`).
- **A refusal's reason:** the 400, 403 or 429 body in the door's raw record (`errors[].code`, `message`, `details`, per the model's `ErrorList`); developers report `QuotaExceeded` on report 429s (GitHub #5152, #5312).
- **Schedules already in place:** `getReportSchedules` with `reportTypes`, read before any `createReportSchedule`.
- **Data Kiosk:** `createQuery` → `getQuery` (`processingStatus`, `dataDocumentId`, `errorDocumentId`, `pagination.nextToken`) → `getDocument` (`documentUrl`). `getQueries` (`processingStatuses`) finds a query already pending, and `cancelQuery` frees the slot. The dataset name, fields, date arguments and readiness come from the dataset's schema (`schemas/data-kiosk/*.graphql`) and its use-case guide, which door.md or the dataset reference should name.
- **Role refusals:** the error "Access to the resource is forbidden" on a report type, which the FAQ explains as "You receive this error when you lack the appropriate roles to request a report" (Reports API FAQ), and which Optimize Calls lists under 403 Forbidden ("your account doesn't have the required Role for the requested operation", among other causes); or a Data Kiosk authorization error naming the field. Both are run-time answers to whether the seller's connection carries that role. For Data Kiosk this answer is the binding one, because Amazon's pages disagree on which role a dataset needs (Data Kiosk API: Brand Analytics for every operation; Correction: Data Kiosk role requirements: Selling Partner Insights for Economics; §J13). "Merchant is not registered in marketplace is invalid" means the seller is not registered in that store (Reports API FAQ).
- **Whether a type still exists:** the report-type-values pages, the SP-API Release Notes and the Deprecation Schedule, read when a type starts answering 400; never a list in a skill.

## Open questions

1. **Data Kiosk concurrency number.** Amazon states a limit on concurrent non-terminal queries "per selling partner and per GraphQL query" and one pending request per query, seller and application, but gives no number. *Settles it:* a Data Kiosk rate-limit page that states it, or a first real run that creates two different queries back to back and records whether the second is refused (429) or queued.
2. **Page size of a Data Kiosk document.** At what size does pagination start? Not stated. *Settles it:* a first real run of a long daily-by-ASIN range that comes back with `pagination.nextToken`.
3. **SQP throughput and per-seller report-type metering.** Amazon staff acknowledged an undocumented system-wide SQP limit. Support texts relayed by developers say report-type limits are per seller account and shared with other apps and Seller Central. Neither is in Amazon's documentation. *Settles it:* a published line on the Analytics Reports page, or the box's own record of `IN_QUEUE` durations over several runs.
4. **Are reports created by other applications visible to `getReports`?** An internal research run saw listings reports for the same seller that it had not created, which suggests yes. But no Amazon page states whether `getReports` and `getReport` return other applications' reports. Data Kiosk states the opposite for its queries. *Settles it:* a Reports API page stating visibility, or a first real run comparing `getReports` with the box's own create log.
5. **Does a request inside a listings cache period get the cached document?** Amazon's sentence names a "cache period" only to warn that a repeat request inside it "may return headers in a different locale than requested"; no Amazon page says a repeat returns the same document. The internal research run witnessed it (three requests, one `reportDocumentId`), and GitHub #1074 reported it in 2021. Still not stated by Amazon, and how long the cache lasts for a given store is not knowable from the record. *Settles it:* an explicit Inventory Reports statement.
6. **"MONTH: 17 months" for SQP.** It sits under "Maximum reporting periods ... using the dataStartTime and dataEndTime parameters" on a report type that may not span more than one period, so the page contradicts itself. It is not stated as a lookback: the SQP entry has no "Maximum lookback windows" heading (only the vendor reports do), and the blog's "usually goes back three years" is about Brand Analytics in general (§I). What it bounds remains unexplained. *Settles it:* Amazon clarifying the page, or a first real run asking for a month 17–18 months back, whose outcome binds.
7. **Are option errors always reported as late `FATAL`, never as a synchronous 400?** For SQP, the report schema states that wrong period dates or more than one store end in "a fatal error"; for other option errors and other report types Amazon states nothing. A malformed `reportType` drew 400 in the day-1 run, so the split seems to be "name checked at once, options later". *Settles it:* a Reports page statement covering options generally. [seat]
8. **Encryption at rest in the box.** Amazon says "Unencrypted report content must never be stored on disk, even temporarily". Day 1 downloaded documents to `/tmp`. Whether the box's landed files meet this is for the office and the door's owner, not this playbook.
9. **Push or poll.** `REPORT_PROCESSING_FINISHED` and `DATA_KIOSK_QUERY_PROCESSING_FINISHED` need a notification destination (SQS or EventBridge, per the Notifications API) owned by the application. Does the box have one? If not, polling is the only route, and the poll interval and "one wait, then tell the seller" rule are the skill's to set (day-2 point 2).
10. **The SQP Seller Central launch date.** *Settled 2026-10-14:* the API gained SQP and SCP on 2025-02-26 (release notes); the Seller Central dashboards launched earlier, with News_Amazon's post "We have launched two new Brand Analytics search dashboards, Search Catalog Performance and Search Query Performance" carrying the timestamp `datetime="2022-04-14T08:54:14.108Z"` (New Brand Analytics search dashboards are now available, Seller Forums, re-opened 2026-10-14). The "about 2021" reading (from the page's relative "5 years ago") is superseded; angles/search-rank-and-volume.md already carries 2022-04-14.
11. **Does a refused call spend a token?** Amazon does not say whether a 400 from `createReport` consumes a token of the bucket. *Settles it:* a Usage Plans statement, or the `x-amzn-RateLimit-Limit` and 429 pattern of a run that records each refusal.
12. **Array filters through the door.** `getReports` takes `reportTypes`, `processingStatuses` and `marketplaceIds` as comma-separated arrays; whether the door's `--query` passes them through unchanged was not tested. *Settles it:* one door call with two report types.
13. **What `enableContentEncodingUrlHeader` changes for the box's download.** Added 2026-04-01; the model describes it, but whether the box's download needs it (GitHub #4762 shows clients broke on the previous encoding change) is untested.
14. **What a `CANCELLED` report's document holds.** Amazon's notification example shows a `CANCELLED` report carrying a `reportDocumentId`, but no page says what that document contains. *Settles it:* the first real `CANCELLED` report that carries one.
15. **Time zone of analytics report dates.** Amazon says the time component is ignored for SQP and states no time zone for Brand Analytics or Sales and Traffic (GitHub #5209, open). *Settles it:* an Analytics Reports statement.
16. **Can a presigned URL be fetched twice inside its five minutes?** Not stated. The box's practice of fetching once makes it moot unless a fetch fails half-way.
17. **SQP date form.** The SQP schema says `format: date`; the ISO 8601 page says "No truncated formats are allowed"; GitHub #5065 saw only the date-time form work, the research run saw both work. *Settles it:* Amazon's reply on #5065, or a pinned form in door.md's entry.
18. **How long after a period closes is SQP requestable?** Openbridge says about 48 hours; the Analytics Reports page states no lag for seller Brand Analytics reports (only for vendor reports); Amazon's seller blog says, of Brand Analytics in general, that data "is generally available within three days, with quarter-end data typically available within one week" (§I), which is not the API report's statement. *Settles it:* an Analytics Reports statement, or the box's record of first-success times.
19. **The Sales and Traffic dataset's removal date.** The release notes say 2026-02-26, the Deprecation Schedule 2026-03-27. Moot for new work (both are past), but a sign the two pages are not kept in step.
20. **Seller Central figures vs API figures.** The FAQ says the two offer different reports and "some reports can be similar but do not contain the same attributes or data". Which Seller Central screen matches which report type is not mapped anywhere read here.
21. **Practitioner coverage.** No agency or vendor writing on report waits, caching or failure handling beyond Openbridge, Saras Analytics and GitHub issues was found. A later pass with a fresh search budget may find more.

## Positions

- **P-report-lifecycle-1.** cx treats a report as finished only when `getReport` reads `DONE`, `CANCELLED` or `FATAL`. `IN_QUEUE` or `IN_PROGRESS` at the end of its one wait is told to the seller as "still queued since <createdTime>", never as a failure and never as "over a day" unless `createdTime` says so. (Verify that report processing is complete; reports_2021-06-30.json)
- **P-report-lifecycle-2.** cx reads `CANCELLED` as "no report from this request". Before telling the seller, it names which of Amazon's three causes fits: an explicit cancel, no data, or a repeat inside the type's period. It never reads `CANCELLED` as zero sales or zero traffic. (Verify that report processing is complete; Reports API FAQ; reports_2021-06-30.json)
- **P-report-lifecycle-3.** cx reads `FATAL` as a failed report. If a `reportDocumentId` is present, it fetches that document as the error explanation, quotes Amazon's words, fixes the named parameter once, and never parses it as data. (Verify that report processing is complete)
- **P-report-lifecycle-4.** cx fetches a document link in the same step it is issued, through the box's own download, and never prints, stores or reuses the link. The link's lifetime is the model's (minutes). (reports_2021-06-30.json; dataKiosk_2023-11-15.json; Retrieve a report)
- **P-report-lifecycle-5.** cx decompresses a report document when `compressionAlgorithm` is `GZIP`, and relies on `Content-Encoding` for a Data Kiosk document. (reports_2021-06-30.json; Building Data Kiosk workflows guide)
- **P-report-lifecycle-6.** Before any `createReport`, cx looks for its own landed receipt of the same ask, then reads `getReports` for that `reportTypes`, store and a `createdSince` window. A record matches on type, store and data range only; because the record does not carry `reportOptions`, the options are matched against the landed receipt, and a record with no receipt is told to the seller as a candidate. It reuses a matching `DONE` report whose `createdTime` still serves the question, or waits on a matching `IN_QUEUE`/`IN_PROGRESS` one, instead of creating a duplicate. (reports_2021-06-30.json `Report`; Analytics Reports "Cache results locally"; Optimize Rate Limits for Application Workloads)
- **P-report-lifecycle-7.** cx takes report type names, `reportOptions` and period rules from door.md's entry, not from memory or trial. When door.md has no entry, it says so and asks rather than probing names against `createReport`. (Analytics Reports; Inventory Reports; Reports API FAQ "Access to the resource is forbidden")
- **P-report-lifecycle-8.** For a Brand Analytics report, cx sends exactly one period per request, from the period's first day to its last (Sunday to Saturday for `WEEK`). A longer window is several reports, said to the seller before any is created. (Analytics Reports)
- **P-report-lifecycle-9.** For Sales and Traffic at `WEEK` or `MONTH`, cx records the expanded range Amazon will use, not the range it typed, and marks a period that ends in the future as partial. (Analytics Reports)
- **P-report-lifecycle-10.** On a 429, cx stops, tells the seller, and waits with back-off before one retry. It never loops `createReport`, and it treats the `x-amzn-RateLimit-Limit` value as the plan in force. (Usage Plans and Rate Limits; Optimize Rate Limits for Application Workloads; Analytics Reports)
- **P-report-lifecycle-11.** cx creates or replaces a report schedule only on the seller's word, after reading `getReportSchedules` for that type. A new schedule silently replaces any existing schedule for the same type and stores. (reports_2021-06-30.json; Schedule and retrieve reports)
- **P-report-lifecycle-12.** cx cancels only its own report and only while it is `IN_QUEUE`, and a Data Kiosk query only while it is `IN_QUEUE` or `IN_PROGRESS`. (reports_2021-06-30.json; dataKiosk_2023-11-15.json)
- **P-report-lifecycle-13.** For Data Kiosk, cx reads `getQuery` to a terminal status. It reads `dataDocumentId` as data, `errorDocumentId` as Amazon's explanation, and `DONE` with neither as "no data for that range". (Verify that query processing is complete; Data Kiosk API)
- **P-report-lifecycle-14.** cx counts a Data Kiosk result as complete only when the query carries no `pagination.nextToken`. Otherwise it issues a new `createQuery` with the same `query` and that token per page, and tells the seller how many pages the figure rests on. (dataKiosk_2023-11-15.json; Data Kiosk Query Processing Finished Notification)
- **P-report-lifecycle-15.** cx does not submit a Data Kiosk query identical to one still pending. On a `createQuery` 429 it waits for or cancels its own pending query rather than resubmitting. (Data Kiosk API; Building Data Kiosk workflows guide)
- **P-report-lifecycle-16.** cx records the dates Data Kiosk actually returned (after the weekly or monthly roll-back and the availability cap), and reads a null for a recent day as "not yet available", not zero. (Seller Analytics Dataset Use Case Guide)
- **P-report-lifecycle-17.** cx lands every report or query document it uses as a file with its report or query ID, type, store, data range, `createdTime` and processing times, and lets a change log cite that file. The ID alone outlives nothing: reports are retained for a limited period, and Data Kiosk results per their `@resultRetention`. (Report Type Values; reports_2021-06-30.json; dataKiosk_2023-11-15.json)
- **P-report-lifecycle-18.** For a merchant listings report, cx tells the seller the file may be a cached copy (inferred from Amazon's "cache period" sentence and witnessed in an internal run) and asks for one store per report. (Inventory Reports)
- **P-report-lifecycle-19.** cx reads a role refusal (a 403 on a report type, or a Data Kiosk authorization error) as "this connection lacks the role for this data" and says so. It does not retry with other report names. (Reports API FAQ "Access to the resource is forbidden"; Optimize Calls to the Selling Partner API, 403 Forbidden; Data Kiosk API; Seller Analytics Dataset Use Case Guide)
- **P-report-lifecycle-20.** A report is fetched in Amazon's three asks: `createReport`, `getReport` on the `reportId` Amazon returned, and `getReportDocument` on the `reportDocumentId` the record carries. cx never polls or fetches an id it typed or remembered rather than read from Amazon's reply. (Request a report; Verify that report processing is complete; Retrieve a report; day-1 run, a self-typed id returned a different report)
- **P-report-lifecycle-21.** The report script adds no rate limiter and no retry of its own. A 429 lands in the receipt with Amazon's own body, and the decision to wait and try again is cx's, said to the seller (P-report-lifecycle-10). (door.md "the door adds no wait and retries nothing of its own"; Resolve Common HTTP and Authorization Error Codes)
- **P-report-lifecycle-22.** cx never creates a report to test whether a report name or an option is valid. (Acceptable Use Policy 2.9, 3.8; Optimize Calls to the Selling Partner API, "Reduce error rates")
- **P-report-lifecycle-23.** The receipt keeps each id with where it came from (the reply that gave it) and the seller and store it belongs to. (reports_2021-06-30.json; Reports API "the format and structure of document identifiers may change")
- **P-report-lifecycle-24.** A downloaded document lands in the seller's tree, never in `/tmp` or another shared place. Whether the tree meets Amazon's encryption-at-rest rule is a platform question for the office, not the skill's to settle. (Retrieve a report; Data Protection Policy)
- **P-report-lifecycle-25.** A reader of a landed report keys on column or field names, notes and strips the UTF-8 byte order mark where Amazon says one is present, and never parses meaning out of an id. (Reports API; Inventory Reports; Reports API FAQ on deprecated columns)
- **P-report-lifecycle-26.** cx waits once, up to the caller's ceiling, for a report it created. If the report is still unfinished, it tells the seller and, on a later turn, reads the same `reportId` again rather than creating another. (Verify that report processing is complete; Analytics Reports "Cache results locally"; Reports API FAQ, a repeat may be cancelled)

### The seat's own (not for a skill)

- S1. Report-type limits appear to be metered per seller account and shared with the seller's other applications and Seller Central. A 429 or `FATAL` on a report may therefore be caused by another tool, which is a reason to ask the seller before any schedule. This rests only on support texts relayed by developers (GitHub #5210) and an internal run that saw reports it did not create.
- S2. Options are validated only when processing starts, so a wrong option costs a queue slot as well as a create token. This rests on Amazon's replies in internal runs, not on a page.
- S3. SQP reports for one seller appear to be processed one at a time, each taking tens of minutes. A playbook should therefore treat SQP as a background job, collected on a later turn, and never as a wait inside one chat turn. This rests on the internal research run and on practitioner reports (#5240, Openbridge).
- S4. Two date forms of one Brand Analytics period (date-only and date-time) gave the same document in an internal run, and the record keeps a date-only `dataEndTime` as midnight at the start of that day. Sending the date-time form ending `T23:59:59Z` keeps the stored end at the period's end. Not stated by Amazon.
- S5. The `REPORT_PROCESSING_FINISHED` route is the clean answer to "one wait, then tell the seller". Whether the box can have an SQS destination is an infrastructure question outside this playbook.
- S6. Do not trust `getReport`'s tutorial example on shape: it shows a `payload` wrapper the model does not have.
- S7. A `FATAL` whose document says only "A client error occurred" may be Amazon's own fault rather than the caller's: GitHub #5350, #5351 and #4701 describe identical requests that failed and then worked with nothing changed. One unexplained FATAL should be told to the seller with Amazon's words, not "fixed" by guessing a parameter.
- S8. SQP waits run from minutes to hours (the research run's 35 minutes; #5065's 7–8 hours; #5240's 30 minutes to an hour inside Seller Central). Any wait inside one chat turn is a guess.
- S9.
